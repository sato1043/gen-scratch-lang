言葉から記法を組む知識
======================

## 概要

言葉で述べた処理をブロック構成へ落とすための知識を、ブロック解説・イディオム集・
手順書として提供する。書いた知識がそのまま機械検査の入力になるため、記述が陳腐化すると
テストが落ちる。

## 外部仕様(what)

- 言葉からブロック構成を組み立てるための知識を、ブロック解説・イディオム集・手順書と
  して読める形で提供する
- イディオム集の各項目は記法を含み、そのまま生成の入力になる
- ブロック解説は core 9 カテゴリとペンを覆い、覆わない範囲を件数と一覧で明記する
- 手順書は手順と自己検査項目を持つ
- 解説の一覧が台帳と一致するかを `--check` で調べられる。一致しなければ終了コード 1
- 作品定義（`project.yaml`）に書けるキー・値の型・省略したときの挙動を、実装を読まずに
  知れる。一覧は実装の表から生成し、散文だけを人が書く
- 生成した層の古びた申告は出どころ（台帳 / 定義の表）を名指し、書き出し直すコマンドを
  添える。コマンドは渡された置き場を反映し、引用で守れない綴りのときは打てないと断る
- 改行だけが違うときは「古い」でなく改行として名指す。知識層と台帳の両方の `--check` が
  同じ扱いをする。書き戻したファイルに改行の混在は残らない
- README を入口として知識層の全ページへ辿れる
- ブロック解説の一覧はブロックごとに引数の型と選択肢の綴りを載せる。型の呼び名は手順書の
  型の表と同じ語を使う
- 選択肢に無いラベルで止まったとき、書ける候補を全件示す
- 手順書は止まったときに見るものを申告の名前で引ける形で持つ。止め方を変えたときは
  移行表へ「これまで通っていた形 → これから」を載せる
- 台帳の項目が 1 つ壊れているだけでも、知識層を組み立てずに止まる。落ちた項目は一覧から
  黙って消えるので、書き上がった層は欠けたことを自分では名乗れない
- 止まったときは「知識層を組み立てられない。申告が N 件ある」と述べる
- `--help` を付けられる。使い方は標準出力へ出て、終了コード 0 で終わる。空の値を渡した旗は
  既定へ倒れず止まり、使い方の記述に無い旗は受け取らない
- エージェント向けの発火点（`.claude/skills/words-to-scratch/`）を持つ。言葉から
  Scratch の作品を作る依頼で発火し、知識層のどのページを見るかと、CLI の起動の形を
  案内する
- 発火点は規則を持たない。記法の書き方・値の型・ブロックの綴り・作品定義のキーは、知識層の
  ページが引き続き唯一の持ち手である
- 発火点が案内するサブコマンドの綴りは、実物へ渡して受け取られることを検査が見張る。README
  から発火点へ辿れることも検査が見る（リンク切れの見張りがその依存に乗っているため）
- 別のページの見出しを名指すときの記法（`パス#見出しの id`）を持つ。書き方は README の
  「ドキュメントの中で見出しを指す」が持つ
- その記法で書かれた参照は、指す先の見出しが消えるか改名されると検査が落ちる。落ちた
  申告はどのページのどの見出しが宙に浮いたかを名指す

## 内部設計(how)

- イディオム集の記法を回帰テストの入力として実行し、往復検査へ通す。知識の記述と検査の
  入力を同一物にすることで、記述の陳腐化を機械が捕まえる
- イディオム集は台帳が扱うカテゴリすべてに触れる。項目数だけを基準にすると、1 つの
  カテゴリに偏った集合でも基準を満たしてしまう
- ブロック解説は 2 層で持つ。カテゴリの説明は人が書き、ブロックの一覧は台帳から生成して
  目印の間へ差し込む。一覧を手で書くと台帳と二重管理になる
- 綴りの衝突は、綴りを組み立てて解析器へ通し、どちらが呼ばれるかを実測して申告する
- 作品定義の仕様も 2 層で持つ。キーと値の型と既定値は実装の 1 つの表
  （`src/definition.ts`）から生成し、組み立て側も同じ表から既定値を読む。2 か所に
  置くと、一覧と実装が食い違っても検査に掛からない
- 生成の目印は出どころごとに分ける。同じ綴りにすると、読む側が一覧の出どころを取り違える
- 知識層の書き込みは全ページを組み立ててから行う。読みながら書くと、途中で失敗したときに
  先行ページだけが新しくなり、半分だけ更新された知識層が残る
- 導線は検査で固定する。README を起点に markdown リンクの推移閉包を取り、知識層の
  全ページへ着くことを見る。書けば増えるが放っておくと減る側の性質なので、減ったことを
  機械が捕まえる
- 手順書が挙げる申告は、ソースの走査でなく実物を動かして照合する。組み立てて作る申告を
  走査は取り落とす。逆向き（実装が申告を増やして手順書が遅れる）は、種類の数を固定して
  捕まえる
- 引数の型の呼び名は台帳の記法の綴りから出す。綴りの分解は `src/notation.ts` が持ち、
  呼び名の表は読み手ごとに残す。突き合わせに使う `expectedAs` は数と文字をどちらも「値」
  として扱うため、読む側の一覧には足りない。知らない綴りは綴りのまま載せず印へ変える
- 散文が名指す数（選択肢を一覧へ置ける長さの根拠・引数を解けない件数・解けない綴り）は
  検査が数える。コメントに書いた数は台帳が動いても落ちて知らせる仕組みを持たない
- 導線の走査には較正を置く。壊れたリンクを含む入力を食わせ、走査が実際に見つけることを
  確かめる。0 件が「健全」なのか「何も見ていない」のかは、それでしか分けられない
- 選択肢は綴りをその場に並べ、長いものだけページ末の表へ回す。閾値は台帳の実測から導く
- 復帰コマンドに埋めるパスは、許される文字を列挙して判定する。3 つの shell すべてで安全な
  単一の引用は存在しないため、守れないと分かったときは打てないと断る
- 台帳の位置は引数で受け、旗にはしない。壊れた台帳を渡す検査のために要るが、旗にすると
  追跡下でない台帳から知識層を組み立てる道ができる
- 見出しを名指す参照は、語から推定せず書き手に記法を課す。実測では「」で囲まれた語
  440 件のうち見出しと一致したのは 5% で、しかも**改名した参照ほど一致しなくなる**。
  壊れたものだけが視界から消えるので、語で分類すると 0 件が「健全」と読める
- 照合は指す先の見出しから id の集合を作り、その中に在るかを見る（許す側の列挙）。
  id は GitHub の作り方（小文字化・記号の除去・空白をハイフンへ）に寄せる。導線の
  見出し 76 件のうち 23 件が素の文字列から動くため、素の一致では足りない
- 較正を二重に置く。参照を 1 件も拾えないと落ちる床と、別の道で数えた件数との等号を
  並べる。床だけだと、1 件抜けても他が増えれば通る空席が残る

## 自動化できないテスト項目

- 手順書の中身が実際に使えるか
    - 目的: 手順に従えば、言葉から記法へ落とせるか
    - 期待結果: 手順の各段で迷わず次へ進め、自己検査項目で誤りに気づける
    - 観察方法: 記法を書いたことのない人が手順書だけを見て 1 つ組んでみる

## 制約・既知の課題

- 手順書の中身が妥当かは機械で測れない（形だけを見ている）
- 手順書の「詰まったときに見るもの」表が実装の申告を覆っているかは見ていない。表は全種を
  載せない方針で、種類が増えたことだけを捕まえて表への追加を書き手へ判断させる
- `build` から公式検証器の拒否へ到達する入力を作れておらず、その経路の申告は検査で
  固定できていない
- 発火点が実際に発火するかはホスト側の照合に依るので、こちらからは測れない。測れるのは
  一覧に現れることと、案内する先が実在することまで
- 発火点が知識層の規則を写していないことは機械で測っていない。語でなく意味の照合になる
  ため、人が読むときの約束として残す（実測では、禁じる側を列挙した到達基準が複製 4 文を
  素通りさせた）
- 発火点が案内する綴りの照合はサブコマンドだけで、旗と引数は見ていない
- 既存の .sb3 を読み解く向き（`read`）は発火点の対象外である
- 見出しを名指す参照のうち、記法（`パス#見出しの id`）に落ちなかったものは見張られない。
  地の文に見出しの名前だけを書いた形は捕まらない
- 見出しの照合は atx（行頭の `#`）だけを見る。下線で書く見出し（setext）と、同じ id が
  2 つあるときの連番（`-1`）は扱わない。どちらも外れたときは黙るのでなく落ちる
