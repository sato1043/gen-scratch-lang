値の綴りを往復で保つ
====================

## 目的

値に含まれる制御文字の扱いを決め、記法と .sb3 の往復が中身を保つようにする。

TASK0010 は名前の綴りを揃えたが、値には触れていない。名前は記法と作品定義の双方に
現れるので揃える相手が居るのに対し、値は記法にしか現れないためである。その結果、値
では 3 方向に食い違いが出る。いずれも申告 0 件・終了コード 0 で通る。

食い違いは憲章の提供価値に直接当たる。記法（.sbk）は「読む・直す・git で差分を追う」
ために渡すものだが、値に NUL が 1 文字あるだけで `grep` も `git diff` も中身を読ま
なくなる。また「3 つは同じ 1 つの記法から導出する」という導出元の一意性は、往復で
中身が変わる時点で成り立たない。

TASK0010 の残課題「値の綴りの扱いが決まっていない」を受け取る。同作業書は「直すには
記法の側の設計が要る」と述べて範囲外に置いた。起票時の実測で、その記法の側に
**TASK0010 が使った印の綴り自体の欠陥**が見つかった（問題節の 4 つめ）。名前と値は
同じ印を共有するので、本作業はその綴りを決め直すところから始まる。


## 目標

- 値に含まれる制御文字が、記法と .sb3 の往復で失われない（SREQ0005）
- 記法と作品定義に、生の制御文字が入らない
- 印の綴りが、記法のどの文脈に置かれてもパースを壊さない（レポーターの中で壊れる
  現状の穴を塞ぐ。名前の側も同じ変更で直る）
- こちらが値の綴りを変えたときは、変えたことを申告する
- 逃がしの規則が、元から印と同じ綴りを持つ値でも破れないことを機械で確かめる


## 非目標

- 名前を記法と作品定義へ同じ綴りで置くという TASK0010 の規則を変えない。**ただし印の
  綴りそのものは名前と値で共有するため、綴りの変更は名前の側にも及ぶ**。変わるのは
  綴りであって規則ではない
- 申告の綴りを決める `neutralize` の許可リストを変えない。載せる側の規則であり、
  往復の可逆性とは別の問題を解いている
- 記法（scratchblocks）の文法そのものを拡張しない。逃がしはこちらの層で閉じる
- ~~値の上限・量の検査を変えない（TASK0012 が持つ）~~（2026-08-23 に取り下げ。受け皿と
  した TASK0012 の該当項目は対象が「名前」に限られ「未実測の推論」と書かれていた。本作業
  が膨張を全値へ広げ実測に変えたので、出力側の線は本作業が置く）
- 制御文字を含む作品を拒まない。読めた範囲を出すに留める方針は TASK0015 の非目標と
  同じである
- `read.mjs` と `serialize.mjs` で名前と値の分け方が別の綴りで書かれている重複は畳ま
  ない（TASK0011 が持つ）。本作業は分岐を利用するだけで、寄せる作業はしない


## 問題

TASK0010 の段階 6 と CP6 が挙げた 3 方向を、起票時に実測で再現した（2026-08-23。
題材は `projects/neko-to-score` を `build` した .sb3 へ値と名前を仕込んだもの）。
4 つめは起票時の分析で新しく見つけた。

### 落ちる方 — 往復で中身が変わる

値 `1行目<LF>2行目<NUL>後` を持つ .sb3 を `read` すると、記法は
`[1行目2行目<NUL>後] と言う` になる。改行が消えている。そのまま `build` で作り直し
て元の .sb3 と値を比べると一致しない。

```
元の値  : "1行目\n2行目\u0000後"
往復後  : "1行目2行目\u0000後"
```

落としているのは逆変換器（`parse-sb3-blocks` の `toScratchblocks`）で、値から C0 制御
文字を落とす。名前は `asName` が先に印へ変えるので落ちない。値には掛けていない。

### 素通しする方 — 生成物がテキストとして読めなくなる

NUL・C1 全域・双方向制御・U+2028/2029・不可視文字は逆に素通しする。上の記法には NUL
が生のまま入っており、`grep` がファイルをバイナリと判定する。

```
$ grep -n 'ずっと' probe-out/ネコ.sbk
Binary file probe-out/ネコ.sbk matches
```

図（SVG）も同じ理由でバイナリ扱いになる。`git diff` も同様に中身を出さない。

### 黙って変わる方 — 変えたことを告げない

印の括弧（`⟪` `⟫`）は `unnameable` が全角の `＜` `＞` へ置き換える。作品の側から
こちらの言葉を名乗れないようにするための守りだが、置き換えたことを申告しない。

```
元の値: "印⟪中⟫後"
記法  : [印＜中＞後] と言う
```

「落としたことは黙らない」という TASK0010 の規律の外側にある。

### 印の綴りが記法の文法と衝突する

TASK0010 が名前へ掛けた印（`<U+000A>` の形）は、**丸括弧のレポーターの中に置かれると
scratchblocks のパースを壊す**。印が使う `<` `>` が、記法では真偽ブロックの記号だから
である。1 行の記法を直接パースして測った。

| 文脈 | 記法 | パース結果 |
|---|---|---|
| ドロップダウン | `[ス<U+000A\>ア v] を (1) ずつ変える` | `changeVar:by:` |
| **レポーター** | `(ス<U+000A\>ア) を [記録 v] に追加する` | **`(none)` / `(none)`** |
| 値の欄 | `[ス<U+000A\>ア] と言う` | `say:` |
| 対照（印なし）| `(スXア) を [記録 v] に追加する` | `append:toList:` / `readVariable` |

実害は往復の破綻として出る。変数名に改行を含む .sb3 を `read` すると図が 1 本作れず、
`build` は `識別子 scratchblocks:end が台帳に無い` で止まる。レポーターの行が壊れた
ことで `もし〜なら` の対応が崩れ、`end` が独立したブロックとして残るためである。
名前を改行なしの綴りへ替えた対照は、同じ手順で往復が通る。

**TASK0010 の決着はこの文脈を含んでいない。** 変数を値として読む `(スコア)` の形は
実用の記法にごく普通に現れるので、名前の側にも同じ穴が開いている。TASK0010 は
`frozen` であり、その状態を動かすかどうかは裁定を仰ぐ（残課題を参照）。

### なぜ中和を値へ広げるだけでは直らないか

名前と同じ `neutralize` を値へ掛けると、素通しは止まるが往復は直らない。記法には
`1行目<U+000A>2行目` と書かれ、`build` はそれを 8 文字の文字列として .sb3 へ入れる。
改行としては解さないので、値は別のものに変わったまま残る。

直すには **`build` の側にも逆写しが要る**。逆写しを入れると、今度は元から
`<U+000A>` という綴りを持つ値が壊れる。逃がしの規則を、こちらが作った印と作品が名乗
った綴りとで見分けられる形にする必要がある。

### 印の綴り

`<U+XXXX>` は使えない。レポーターの中でパースを壊すことを実測した（問題節の 4 つめ）。
綴りが満たすべき条件は 3 つある。

1. scratchblocks が構造に使う文字を含まない
2. 作品の側から名乗れない。元から同じ綴りを持つ値を、こちらが作った印と見分けられる
3. 図と作品定義へ出ても読める（子どもが読む画面に出る）

**既存の印の括弧（`⟪` `⟫`）へ統一する**（2026-08-23 裁定）。段階 1 で候補 5 つを測り、
条件 1 はいずれも満たすことが分かったので、条件 2 と 3 で選んだ。この括弧は入力に
現れたら必ず守りを通るので条件 2 の下地が既にあり、`⟪読み取れない: …⟫` として図へ出た
実績が条件 3 を裏づける。測定は作業記録の段階 1 にある。

構造に使う文字のうち実際に壊すのは `<` だけである（`>` だけを含む綴りは通る）。ただし
印は対で使うので、両方を避ける。

### 自己衝突を避ける順序

規則は順序で閉じる。

1. `read` は値の `⟪` `⟫` を先に印の形（`⟪U+27EA⟫` `⟪U+27EB⟫`）へ変える
2. 続けて C カテゴリの符号位置を `⟪U+XXXX⟫` へ変える
3. `build` は `⟪U+XXXX⟫` を符号位置へ戻す（`⟪U+27EA⟫` は `⟪` へ戻る）

1 を先に済ませるので、2 が作った印と作品が元から持っていた綴りが混ざらない。`build`
の逆写しは 1 通りに決まる。

**「黙って変わる方」もこの規則で消える。** 現在 `unnameable` は入力の `⟪` を全角の
`＜` へ置き換えて落としているが、1 の形（印へ変える）に替えれば可逆になる。守りの
役目は変わらない ── どちらも作品の側からこの括弧を名乗れなくする。

### 掛ける場所

**規則は `notation.mjs` が持つ**（`spelled` と `restored`）。読む側と書き戻す側の双方が
同じ規則を要するので、どちらかへ置くと同じ規則が 2 か所に分かれる。判定（どの符号位置を
印にするか）は `errors.mjs` に 1 つだけ置き、綴りは呼ぶ側が選ぶ ── 申告は端末へ出すだけ
なので山括弧のままでよく、記法の側だけが印の括弧を使う。

**`read` 側は名前と値を分けない。** 起票時の設計では分岐（`NAME_FIELDS` / 原始値の
種別 11・12・13）で守りを選び分ける想定だったが、記法へ載る綴りである点で 2 つに違いが
無く、分けても綴りが揃うだけだった。分岐を消して 1 つの守りへ通す。

**`build` 側も名前と値を分けない**（2026-08-23 裁定）。値だけ復して名前を印のまま残す
状態は、同じ規則が対象によって効いたり効かなかったりする割れになる。復すのは .sb3 へ
入れる直前の 4 経路である。

| 経路 | 何を入れるか |
|---|---|
| `fieldValue` | 欄の値と名前を `block.fields` へ |
| `shadowFor` | 原始値・メニューの影へ |
| `namedPrimitive` | レポーターが指す名前（`(スコア)` の形）へ |
| `project.mjs` の宣言を集める口 | 作品定義が宣言する名前へ |

**記法の側と作品定義の側の双方で復す。** 片方だけ復すと綴りが割れ、宣言と参照が別の
名前を指す。実際に定義の側だけ復さない破壊を当てると「変数が宣言されていない」で
止まった。

申告の材料（`mismatchOf` 3 か所・`numberMismatch`）は復さない。申告は記法のどこを直せば
よいかを示すので、記法に書かれている綴りのまま見せる方が読み手と対応が取れる。

**`read` 側と `build` 側で名前と値の分け方が別の綴りで書かれていた**（数値コードと
opcode 名）。本作業で双方の分岐が不要になったので、その重複自体が消えた。TASK0011 が
扱う残りの重複には手を付けない。

## 検証

### 概要

- 往復の検査は**値の一致を最初に assert する**。終了コードや申告の文言を先に置くと、
  値が変わっていても別の理由で落ちて緑に見える
- 印の綴りは、記法を直接パースして測る。往復の成否で測ると、壊れた理由が綴りなのか
  逆写しなのか分からない
- 検査の入力は符号位置の全域を走査して作る。代表値を数個置く形にすると、次に増えた
  区分が漏れる
- 生成物がテキストとして読めることは、`grep` の判定そのもので測る。「NUL が無い」を
  測ると、判定を変える他の要因（不正な UTF-8 等）を見落とす

| `ス<U+000A>ア`（逃がしなし）| `append:toList:` / `(none)` / `(none)` |
| `ス<U+000Aア`（`<` だけ）| `(none)` / `(none)` |
| `スU+000A>ア`（`>` だけ）| `append:toList:` / `readVariable`（通る）|

**逆変換器が逃がすのも `<` `>` だけである。** 候補 5 つを `toScratchblocks` へ直に
渡し、書き起こされた綴りを見た。現行だけが `>` を `\>` へ逃がし、他は素通しする
（生の改行は落ちる。既知）。

**候補はいずれも 3 つの文脈を通る。** ドロップダウン `[… v]`・レポーター `(…)`・
値の欄 `[…]` の 3 通りで測り、現行の `<>` 以外はすべて対照と同じ識別子を返した。

| 候補 | 逆変換器 | 3 文脈 | 追跡下の出現 | 日常語での出現 |
|---|---|---|---|---|
| `<>` 現行 | `>` を逃がす | **レポーターで壊れる** | — | — |
| `⟪⟫` 印の括弧 | 素通し | 通る | 8 ファイル（実装と説明）| 稀 |
| `⟦⟧` 白角括弧 | 素通し | 通る | 0 | 稀 |
| `«»` ギュメ | 素通し | 通る | 0 | 欧文で頻出 |
| `【】` 隅付き | 素通し | 通る | 0 | 日本語で頻出 |
| `＜＞` 全角 | 素通し | 通る | 3 ファイル | `⟪⟫` の置換先に使用中 |

追跡下の出現はいずれも実装とドキュメントの記述で、作品データには無い。`＜＞` は
`unnameable` が `⟪⟫` の置換先に使っており、印にすると役割が二重になる。

**推奨は `⟪⟫` への統一。** 選ぶ理由は 3 つある。

1. **自己衝突の守りが既にある。** `unnameable` が入力から `⟪⟫` を必ず落とすので、
   作品の側はこの括弧を名乗れない。新しい文字を選ぶと、その文字にも同じ守りを別に
   立てることになる
2. **書体の実績がある。** `⟪読み取れない: <opcode>⟫` として既に図へ出ている
3. **守りが 1 つで済む。** 現在は「落として `＜＞` へ変える」ため可逆でないが、
   落とす代わりに印（`⟪U+27EA⟫`）へ変えれば、同じ 1 つの規則で「黙って変わる方」も
   同時に消える

対抗は `⟦⟧`。役割が分かれて読みやすい（`⟪⟫` はこちらの言葉・`⟦⟧` は符号位置）が、
守りが 2 セットになり、書体の実績も無い。

### 段階 4・5: 値の逃がしと逆写し（2026-08-23）

2 つが揃って初めて往復が閉じるので続けて実装した。

**読む側は名前と値を分けない。** 記法へ載る綴りである点で 2 つに違いが無く、分けても
綴りが揃うだけだった。区別が要るのは書き戻す側で、そちらは名前を宣言と突き合わせる
ために印のまま扱い、値だけを符号位置へ復す。

**印の括弧も同じ形へ変える。** 落として全角へ置き換えていたころは、置き換えたことを
申告せず元へも戻らなかった。括弧を先に印へ変えてから符号位置を印へ変えるので、出来
上がった綴りに現れる括弧はすべてこちらが作ったものになり、復し方が 1 通りに決まる。

| 入力 | 記法での綴り | 復した値 |
|---|---|---|
| `a` + 改行 + `b` | `a⟪U+000A⟫b` | 元に戻る |
| `印⟪中⟫後` | `印⟪U+27EA⟫中⟪U+27EB⟫後` | 元に戻る |
| `⟪U+000A⟫`（自己衝突）| `⟪U+27EA⟫U+000A⟪U+27EB⟫` | 元に戻る |
| `x` + NUL + `y` | `x⟪U+0000⟫y` | 元に戻る |

**綴りの規則は `notation.mjs` へ集めた。** 読む側と書き戻す側の双方が同じ規則を要する
ので、どちらかに置くと同じ規則が 2 か所に分かれる（TASK0011 が畳もうとしている型の
重複を新たに作ることになる）。

**名前の中身は元へ戻らない。** `ス` + 改行 + `ア` は `ス⟪U+000A⟫ア` として .sb3 へ入る。
記法と作品定義が同じ綴りを持つので往復は閉じ、到達基準（往復が終了コード 0 で通る）は
満たす。中身まで復すには作品定義の側にも印を解く規則が要り、それは利用者が手で書く
定義の書き方を変える判断になる。残課題へ立てた。

**書き込みの経路でバックスラッシュが 1 段消えた。** 復す側の正規表現へ `\+` を書いた
つもりが `+` になり、量詞として読まれて何も復さなくなった。文字クラスで書き直し、
理由をその場へ残した。

**既存の検査を 2 つ書き換えた。** 値に印を掛けないことを固定していた対照は、掛けることを
測る側へ反転した。偽の印を防ぐ守りの検査は、括弧が消えることでなく偽の印が立たない
ことを測る形にした ── 括弧の不在は手段であって目的ではない。
