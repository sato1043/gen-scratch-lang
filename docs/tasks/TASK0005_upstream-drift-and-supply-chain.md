上流のずれと供給網を確かめる
============================

## 目的

台帳の正しさが依存する上流（scratchblocks・scratch-blocks）と、手で書いた
入力表の関係を、機械で確かめられる状態にする。台帳は 4 つの生成元から
組み立てるが、そのうち手書きの 675 行は「書いたときは正しかった」以上の
保証を持たない。

TASK0001 の CP6 レビューで、手書きの表に再導出の照合が無いこと、開発依存を
本体のコードが import していること、検証が 1 台の環境でしか走っていないことが
指摘された。


## 目標

- 上流の現在の版から再導出できる表を照合し、食い違いを機械で示す（SREQ0002）
- 再導出で覆えない表について、出典と版を機械可読に記録し、上流の版が動いた
  ことを検知できるようにする（SREQ0002）
- 本体のコードが開発依存を import している箇所を解消する
- 検証が開発機以外でも走ることを示す
- 概要設計が宣言する型検査（`tsc --checkJs`）を、導入するか記述を落とすかで
  決着させる

（残る 3 つの目標は内部品質であり、提供要求としては採番しない。2026-08-18 裁定）


## 非目標

- 上流の版を上げること自体を目的にしない（ずれを見えるようにするのが目的）
- 台帳の生成元を新たに導入しない。既に出典として効いているものを宣言へ
  書き起こすのは、増やすことに当たらない（2026-08-18 裁定）
- 出典が旧版で固定された表を、その旧版を pin して照合対象にしない。pin した
  版は二度と動かず、照合は永久に一致し続けるため検査として働かない
  （2026-08-18 裁定）


## 問題

- 手書きの表は 3 ファイル 675 行ある。`catalog --check` は台帳が生成器の
  出力と一致するかを見るが、生成器はこの表を入力に取るため、表の誤りは
  そのまま通る。見張っているようで見張れていない
- **宣言している生成元が 4 つで、実体は 7 つある**。`src/catalog.mjs` の冒頭は
  生成元を 4 つ（scratchblocks の定義表・同じく日本語辞書・scratch-blocks の
  ブロック定義・手書きの例外表）と書くが、手書きの表が「機械で書き出した」もので
  ある以上、その出典（scratch-l10n・旧版 scratch-blocks・scratch-vm）が実質の
  生成元として効いている。宣言が実体を写していない

  概要設計の表に置く。現行の依存から書き出し直せるのは選択肢の対応（243 行）

先頭コメントが出典を明記しているので、そこから棚卸しした。

|---|---|---|---|

| `MENU_OPTIONS` | 36 | 内部値は scratch-blocks 0.1.0-prerelease.20221207082607、ラベルは現行 2.1.19 | 不可。現行はメニュー定義が空で、中身を scratch-gui が実行時に埋める |

### 覆う範囲と覆わない範囲を分けて申告する

照合が本物の検査として働くのは `OPTIONS` だけである。出典が現行版なので、上流が
動けば結果が変わる。ここは書き出し直して追跡下の表と突き合わせる。

残りは照合の代わりに**出典の版を機械可読に記録し、版が動いたら鳴らす**。ずれの
中身までは分からないが、確かめ直す必要が生じたことは分かる。台帳は既に
`生成元`（scratchblocks・scratch-blocks の版と手書きの表の指紋）と`覆わない範囲`の
構造を持つので、そこへ寄せる。TASK0001 が採った「覆えないブロックを申告する」形と
同じ構えであり、TASK0004 の残課題（`scratch-parser` の版を機械可読に残すか）も
同じ仕掛けに乗る。

### 依存の整理

`src/roundtrip.mjs` が使う `parse-sb3-blocks` は逆変換の中核で TASK0002 が乗るため、
本体依存へ移す。

`src/opcodes.mjs` が使う `scratch-blocks` は台帳生成にしか要らず 21MB あるため、
開発依存のまま生成側へ閉じ込める。ただし `src/catalog.mjs` は台帳を組み立てる
`buildCatalog` と、書き出し済みの台帳を読む `loadCatalog` の両方を持ち、後者は
本番経路にある。読む側は `catalog/blocks.json` を読むだけで `scratch-blocks` を
要らないので、割り方は 2 通りある — ファイルを生成側と読み取り側に分けるか、
`opcodes.mjs` の import を遅延させるか。着手時に測って決める。

### 供給網の統制

`npm ci` の強制と `ignore-scripts` の扱いは、CI を置く段階で同時に決める。CI が
無い今は人手の規律しか無く、統制の置き場そのものが存在しない。

## 作業記録

### 段階 1: 依存の整理

`src/catalog.mjs` を読む側と組み立てる側に割った。読む側（`loadCatalog`・`agentFor`・
`stampedCatalogOf`・`catalogDrift`）は追跡下の `catalog/blocks.json` を読むだけで開発
依存を要らない。組み立てる側は `tools/build-catalog.mjs` へ移し、`src/opcodes.mjs` も
`tools/opcodes.mjs` へ移した。`catalog` サブコマンドは利用者向けの入口から外し、
開発者向けの `tools/cli.mjs` が持つ。README も使い方と開発に節を分けた。

**解決の位置を測り直したところ、着手前の見立てが誤っていた。** `opcodes.mjs` は
トップレベルで `scratch-blocks` を import しておらず、`packageRoot()` の中の
`require.resolve` で呼ばれたときにだけ解決する。静的 import グラフに開発依存は現れず、
`render` / `build` / `knowledge` は巻き込まれていなかった。落ちるのは `catalog` を
実行したときだけである。着手前に書いた「本番経路が確実に壊れる」は行き過ぎだった。
分ける価値は残る（利用者向けの入口が開発者向けの経路を抱えている状態そのものが、
宣言と実体の食い違いである）が、緊急度の見積もりは下がる。

`parse-sb3-blocks` は `dependencies` へ移した。こちらはトップレベルの `require` で、
モジュールを読み込んだ時点で解決する。現在の読み込み元はテストだけだが、TASK0002 が
本番経路へ載せる。

分けた状態は放っておくと戻る。指定子を 1 つ書き足せば経路が復活し、開発機には開発
依存も入っているため検証は素通りする。`test/dependencies.test.mjs` を置いて、本体の
ソースが開発依存を指していないことを見張る。散文のコメントで名前に触れるのは通し、
引用符で囲まれた指定子だけを見る（モジュール指定子は必ず囲まれるため）。

TASK0001 の検証手順に書かれた `node src/cli.mjs catalog --check` は、この移設で
`node tools/cli.mjs catalog --check` になる。当時の記録として書かれているため
TASK0001 側は改めない。

### 段階 2: 選択肢表の再導出

上流から選択肢の対応を書き出し直す `tools/derive-options.mjs` を置いた。ブロック定義
（`src/blocks/*.ts`）の `[Blockly.Msg.X, '値']` の組から内部値を取り、同梱の
`msg/scratch_msgs.js` の `locales['ja']` から日本語ラベルを引く。

**日本語ラベルの出典を scratch-l10n から scratch-blocks 同梱へ替えた。** 計画では
scratch-l10n を依存へ足すつもりだったが、実際に足したところ `npm audit` が 11 件
（critical 5・high 2・moderate 4）を報告した。すべて scratch-l10n → transifex →
request / mocha の連鎖から来ており、TASK0004 で 0 件を実測した供給網が汚れる。

同梱の見出しで足りるかを測ると、284 件中 283 件が scratch-l10n の `editor/blocks/ja.json`
と一致し、選択肢のラベル（「スペース」「マウスのポインター」「上向き矢印」等）はすべて
引けた。差は `DUPLICATE`（コンテキストメニューの語で選択肢ではない）と `SENSING_ONLINE`
の値 1 件のみ。よって scratch-l10n を外した。依存は段階 1 の終了時と同じに戻り、
`npm audit` も 0 件へ戻っている。

**出典が 1 つに揃う利点もある。** 従来は内部値が scratch-blocks 2.1.19、ラベルが
scratch-l10n 6.1.110 と別の版から来ており、版がずれる余地があった。同じ版から取れば
その余地が消える。

書き出した結果は追跡下の表と一致した（19 ブロック / 151 組・差 0 件）。取りこぼしの
較正として、選択肢の要素数と読めた組の数を欄ごとに照合している。値は単引用符と二重
引用符の双方で書かれ（`"don't rotate"`）、単引用符だけを見ると黙って落ちるため。

### 段階 3: 覆わない範囲の申告

`catalog/provenance.mjs` に手書きの表 8 つの出典を機械可読で置き、台帳の `表の出典` へ
載せた。種別は再導出できるかで 4 つに分ける（導出・旧版・別出典・手書き）。照合で
見張れるのは `OPTIONS` だけなので、残る 7 件を「見張れていない範囲」として申告する。

**当初は `覆わない範囲` へ入れたが、解説の生成が `(名前なし)` を 7 件並べた。** あの欄が
数えるのは台帳に載らなかったブロックであり、表はブロックではない。欄を分けて解決した。
混ぜていたら、生成物に意味を成さない行が残ったまま緑が返っていた。

旧版から取った表（`MENU_OPTIONS`・`SHADOWS`）は照合できないので、代わりに「確かめた
時点の scratch-blocks の版」を持たせ、今の版と違えば確かめ直しを促す。何がどう変わった
かまでは分からない。分かるのは、確かめたときの前提が動いたことだけである。

### 段階 4: 環境の追加

`.github/workflows/verify.yml` を置いた。ubuntu-latest の Node 20 と 22 で検証を回し、
追跡下の生成物（台帳・解説・選択肢の対応）が今の入力から組み立て直したものと一致するか
も見る。生成物は手元で書き出して commit するため、書き出し忘れは手元では気づけない。
`npm audit` は別のジョブに置いた。

**CI が置いた初日に 2 つの穴を検出した。** どちらも手元では見えない類のものである。

1 つ目は**検証の起動そのものが Node 22 で通らない**こと。`node --test test/` の位置引数の
読み方が版で割れており、20 はディレクトリとして読み、22 は glob として読む（Node 22 の
ドキュメントが「glob パターンを渡す」と明記している）。`package.json` は 22 を engines へ
宣言しているのに、22 では検証が 1 件も走らない状態だった。引数なしにすると既定の探索が
作業ディレクトリを丸ごと見るため、手元では退避してある過去の版まで拾い 278 件中 56 件が
落ちた。追跡下の `test/` のファイルを自分で数えて並べて渡す `tools/run-tests.mjs` に寄せ、
両方の版で 200 件が通ることを確かめた。

2 つ目は**開発依存なしの検証が空振りしていた**こと。`npm prune --omit=dev` は
「up to date」を返して何も外さず、その後の実行は開発依存が入ったままの環境で通っていた。
緑だが何も測っていない。入れ直す形（`npm ci --omit=dev`）に替え、`scratch-blocks` が
実際に不在であることを先に確かめてから走らせるようにした。ログの「何も消していない」と
いう 1 行を読まなければ、そのまま通過していた。

直した後の実行（run 32108315263）は 3 ジョブすべて成功し、Node 20 と 22 の双方で 200 件が
通った（スキップ 0）。開発依存の不在を確かめる段も通っており、その後の .sb3 の組み立ては
本番の依存だけで走っている。

### 段階 5: 型検査

判断材料を実測したうえで、ユーザーが「導入する」と裁定した（2026-08-18）。

| 測ったもの | 値 |
|---|---|
| `tsc --checkJs` のエラー | 189 件 |
| うち `@types/node` の欠落によるもの（TS2591）| 92 件 |
| 暗黙の any（TS7006 / TS7053）| 59 件 |
| 判別ユニオンの絞り込み不足（TS2339）| 12 件 |
| catch 変数が unknown（TS18046）| 10 件 |
| 型注釈に占める any の割合（`src`）| 38%（228 個中 87 個）|
| 型注釈に占める any の割合（`tools`）| 10%（120 個中 13 個）|

**この時点の私の評価は「実際の不具合は無い」で、導入しないことを推奨した。裁定は逆で、
入れてみた結果、裁定の方が正しかった。** 92 件の TS2591 に埋もれて中身を見ていなかった。
@types/node を入れて雑音を落とすと、宣言と実体の食い違いが 3 件残った。

| 見つかった食い違い | 宣言 | 実体 |
|---|---|---|
| 台帳の項目の `args` | 引数名の配列（`string[]`）| `{name, kind, notation, shadow, ...}` の配列 |
| 台帳の項目の `alsoCovers` | 宣言が無い → 直して `string[]` | `{opcode, args}` の配列 |
| 影を補う規則 `FALLBACK` | `Record<string, string>` | 値が null を取りうる |

2 つ目は**この作業の中で typedef を「実体に合わせた」直後に書いた宣言が誤っていた**
もので、型検査が自分の書いた宣言を捕まえた形になる。「自分が今書いた宣言ほど疑う動機が
生まれない」がそのまま出た。

導入の内訳は次のとおり。189 件から 0 件まで下げた。

| 段 | 残り |
|---|---|
| `@types/node` を入れる | 189 → 94 |
| 型を持たない上流 5 つを `types/externals.d.ts` で宣言 | 94 → 89 |
| 手書きの表へ `Record` の型を付ける | 89 → 77 |
| 台帳の項目の typedef を実体に合わせる | 77 → 70 |
| 投げられたものから理由を取る口を `src/errors.mjs` へ 1 つにまとめる | 70 → 48 |
| 残りのコールバックと索引に注釈を付ける | 48 → 0 |

`src/errors.mjs` は型を通すために作ったが、潜在的な不具合も消えた。catch が受け取るのは
Error とは限らず、`message` を直に読むと Error でないものを受け取ったときに報告へ
`undefined` が出る。

`npm run typecheck` を足し、CI の検証ジョブへも載せた。**配線するまでは、直したつもりの
状態が壊れても誰も気づかない。** 実際に効くかは、上で見つけた食い違いの 1 つ
（`alsoCovers` を `string[]` へ戻す）を当てて確かめた。狙った箇所が
「`opcode` は `string` に無い」で落ちる。

### CP6 の第三者視点レビュー

11 観点（10 特性 + 供給網の攻撃面 depth）を並列で回した。指摘は約 120 件、収束後の
高が 7 件。詳細は `.claude/tmp/review/20260818-task0005/`。

**宣言した不変条件 3 つは充足が裏取りされた。** 移設で落ちた挙動は検出されず、
導出の 151 組は独立に数え直して一致し、`meta.agent` の刻印も台帳の後方互換も
保たれている。

**一方でこの作業が置いた検査 3 つに、宣言した守備範囲を満たさないものが見つかった。**
いずれも複数観点が独立に収束した。緑が健全さを証明していない構造にあたる。

| 穴 | 実測 | 直し方 |
|---|---|---|
| 開発依存の見張りが `src/` 直下の非再帰のみ。`catalog/` は本体の静的グラフの内側なのに走査外 | `catalog/shadows.mjs` へ指定子を足しても pass | 走査を入口から辿る形へ替え、検出器を指定子の形で見るようにした |
| 較正が読み取りと同じ手掛かり（開き括弧）に依り、括弧で始まらない要素は双方から見えない | spread・識別子・関数呼び出し・`.concat` の 4 形すべてで問題 0 件 | 区切りの数で数える形へ替え、配列の外側で足す形には別のガードを置いた |
| 自前データ構造の `any` が境界で型を止める | `buildCatalog`・`loadCatalog` の戻りが `any` | 台帳の形を読む側で定義し、作る側がそれを参照する向きにした |

3 つ目の向きが重要で、形を作る側で定義すると、読む側が形を知るために生成側を参照することに
なり、開発依存を分けた意味が消える。

**設計上の限界も記録する。** `derive-options`・`catalog --check`・`生成元` の指紋は、
いずれも
被検査対象と同じ出所から作ったオラクルであり、改竄検知ではなく変化検知にすぎない。
汚染された値が一度受け入れられると以後は永久に緑を返す。完全性を実際に支えるのは
lockfile の integrity と `npm ci` の強制と git 履歴の保護の 3 点で、
3 番目（`main` のブランチ保護）が空である。


### 段階 6: 実行環境の版の追随（追補 2026-08-19）

Node 20 は 2026-04-30 に EOL を迎えていた。開発機の常用も CI の matrix の半分も、
サポートの切れた版の上に載っていた（nodejs/Release の `schedule.json` で確認）。

`engines` の値（`^20.19.0 || ^22.13.0 || >=24.0.0`）は jsdom 29.1.1 のものと文字列まで
一致する。依存が要求する下限を写したもので、版を選んだ結果ではなかった。

**移行の可否を、既存の `node_modules` のままの実測で済ませかけた。** Node 20 用に入れた
バイナリが Node 24 のプロセスで 301 件を通したので、ネイティブ依存（canvas・
@resvg/resvg-js）が N-API で ABI 非依存だという見立ては裏が取れた。だがそれは移行後の
状態ではない。ユーザーの指摘で入れ直したところ、npm 自体が 10.8.2 から 11.17.0 へ上がり、
既存の `node_modules` では決して出ない警告が出た。

```
npm warn allow-scripts 1 package has install scripts not yet covered by allowScripts:
npm warn allow-scripts   canvas@3.2.3 (install: prebuild-install -r napi || node-gyp rebuild)
```

`canvas` の `files` に `build/` は無く、`npm ci` は `node_modules` を空から作る。それでも
`build/Release/canvas.node` が生成され PNG を吐いたので、今回は実行されている。ただし
「not yet covered」の文言どおり、npm が既定をブロック側へ倒せば canvas は静かに壊れる。
残課題へ記録した。2026-08-18 の `ignore-scripts` の裁定（切ると導入が成立しない）が、
npm の既定の側から揺らぐ形になる。

| 測ったもの | 結果 |
|---|---|
| Node 24 + 既存の `node_modules`（npm 10 で入れたもの）| 301 件 pass |
| Node 24 + npm 11 で入れ直し | 301 件 pass・skip 0・todo 0 |
| 型検査（`@types/node` 24.13.3）| 0 件 |
| `catalog --check` / `options` / `knowledge --check` | いずれも exit 0 |
| `.sb3` の組み立て | exit 0 |

`@types/node` は `engines` の下限へ揃えた。26 系のままだと下限に無い API が緑になる
（M-3）。24 系へ落としても型検査は 0 件のまま通り、下限と型の範囲が一致した。

`npm ci --omit=dev` を挟む開発依存の不在の検査だけは、手元で回すと入れ直しが要るため
CI に委ねた。**この 1 項目は手元では未検証**である。
