申告の扱いを 1 通りに揃える
===========================

## 目的

同じ「誤りを伝える」判断が、コマンドごと・出力ごとに割れている状態を畳む。今は
台帳の申告を `build` が持ち上げ、`knowledge` が止め、`read` が捨てる。中和は申告と
要約に掛かるが `.sbk`・`project.yaml`・SVG には掛からない。同じ入力に対して、
どの口から出るかで扱いが変わる。

TASK0002 の CP6 が挙げた束のうち、申告の生成と伝播に当たるものを受け取る
（2026-08-20 に別作業へ下ろす裁定）。TASK0007 が申告の語彙と止め方を整えた続きに当たる。


## 目標

- 台帳の申告の扱いを 1 つに決め、3 通りの割れを畳む（SREQ0007）
- 中和の掛かる範囲を出力ごとに割らない（SREQ0007）
- `read` の終了コードの契約を他のコマンドと揃える（SREQ0008）
- 到達しうる申告の受け口に検査を置く
- 申告が次の一手へ繋がる（戻り道・逃げ道・上限の緩め方を示す）（SREQ0004）
- オプションの扱いと使い方の説明が、コマンドごとに割れていない（SREQ0009）
- 成果物へ載せる断りが、その実行で実際に起きたことを述べる（SREQ0005）

後半の 3 つは 2026-08-22 に足した。段階 5 の項目群が目標のどれにも入らないことを分析で
見つけ、範囲へ含める裁定を受けたため（裁定記録を参照）。

帰属は同日に規約の 2 ゲートで判定した。「受け口に検査を置く」は知覚ゲートを通らない
（外部仕様に知覚項目を足さず、内部品質だけを上げる）ので ID を持たない。「オプションの
扱いと使い方の説明」は**新規採番する裁定**を受け、CP8 の `spec-derive` が SREQ0009 を
割り当てた。由来は新設した BREQ0004（4 つのコマンドを 1 つの道具として扱える）である。


## 非目標

- 申告の文言そのものの書き直しを主目的にしない（TASK0007 が扱った層）
- 誤りの自動修正を足さない。示すに留める（SREQ0004 の非目標と整合）

## 概要設計

### 3 経路が今どう割れているか

`loadCatalog` は `{ raw, byIdentifier, problems }` を返す。壊れ方は 2 つある。

- **台帳を読めない**: `raw` が `null`。JSON として読めないか、最上位の型が違う。1 つも
  解けない。`catalog.mjs` が申告の名として既に使っている綴りに合わせる
- **項目だけが壊れている**: `raw` はあるが `problems` が空でない。項目単位で型が違うか
  識別子が無い。その項目だけが `byIdentifier` から落ち、残りは引ける

| 経路 | 台帳を読めない | 項目だけが壊れている |
|---|---|---|
| `build` | 持ち上げて止める（非 0） | 持ち上げて止める（非 0） |
| `knowledge` | 止める（非 0） | 止める（非 0） |
| `read` | 申告を返して止める（非 0） | **黙って捨てる**（0 でありうる） |

起票時は「`build` が持ち上げ・`knowledge` が止め・`read` が捨てる」の 3 通りと書いた。
実装を読むと、**振る舞いが割れているのは `read` の「項目だけが壊れている」場合の
1 か所だけ**である。残りの割れは振る舞いでなく**申告の見出し**にある ── `build` は
台帳の申告を「`.sb3` にできない箇所」と呼び、`knowledge` は「台帳を使えない」と呼ぶ。
同じ原因が入口の名前で呼び分けられ、`build` に至っては原因を言い当てていない。

さらに `read` と `knowledge` は `loadCatalog()` を引数なしで呼ぶ。壊れた台帳を渡せるのは
`build` だけ（`options.catalogPath`）で、**残り 2 経路には破壊を当てられない**。揃えた
ことを検査で固定するには、まずここを開ける必要がある。

### 揃える先

**「捨てない」を規則にする**。持ち上げた先で止めるかどうかは、その申告が結果を左右
するかで決める ── `build` と `knowledge` は台帳が欠ければ成果物が欠けるので止める。
`read` は台帳に無い opcode を印で示す道を既に持っており、止めると読める作品まで
読めなくなる（TASK0015 が広げた方向と正面から反する）。

3 経路が通る 1 つの規則はこう書ける。

> 台帳の申告は捨てない。申告が 1 件でもあれば終了コードは非 0 にする。
> 成果物を書くかどうかは、申告と別に決める。

これは TASK0009 が `read` の出力について下した契約（読めたものは書き出し、申告があれば
非 0）と同じ形である。新しい規則を足すのでなく、既に決まっている契約を台帳の申告へも
通す。

### `read` の終了コードを他のコマンドと揃えるか

揃えるのは**終了コードの規則**であって、**書き出しの規則**ではない。

- 共通の規則: 申告が 1 件でもあれば非 0。3 経路とも既にこれを満たしている
- 分かれてよい点: 部分的な成果物を残すか。`build` の生成物は Scratch が開けなければ
  価値が無いので残さない。`read` の生成物は部分でも読み手に価値がある（TASK0009 の裁定）

この 2 つを分けて書けば「同じ規則で説明できる」を満たす。書き出しまで揃えると
TASK0009 の裁定を覆すことになるので、揃えない。

### 中和を出力を書く 1 か所へ寄せる

標準出力・標準エラーは `errors.mjs` が 1 か所で持ち、`test/errors.test.mjs` が走査して
見張っている。ファイルの側には同じ仕組みが無い。

寄せ方は `announce` と同じにする ── **地の文はそのまま通し、外から来た値だけを逃がす**。
出力の全体へ中和を掛ける形は取れない。`.sbk` は記法そのもので、改行と字下げが意味を
持つ（丸ごと中和すると `build` へ戻せない）。逃がし方も出力の種類ごとに違う
（markdown は `|` と `[`、YAML のコメントは改行、SVG は XML のコメント、記法は印の括弧）。

したがって「1 か所」は**逃がす関数の置き場**でなく、**出力を書く口**である。口は
`placeAll` に既にある。ここへ「この出力はどの逃がし方を通ったか」を宣言させ、宣言の
無い出力を足したら落ちる形にする。測るのは「新しい出力の種類を足したときに漏れるか」で、
既存の出力が通ることだけを見ても次に足す出力への効き目は分からない。

### `--locale` が支配する範囲

`--locale en` を実測した（2026-08-22・`out/neko-to-score.sb3`）。

| 成果物 | locale が効くか | 中身 |
|---|---|---|
| `.sbk`（記法）| 効く | `when @greenFlag clicked` / `move (…) steps` |
| 記法の中の印 | **効かない** | `読み取れない: <opcode>`（`read.mjs` の `MARK`）|
| `summary.md` | 効かない | 108 行すべて日本語 |
| `project.yaml` | 効かない | 欄名も断りも日本語 |
| 申告（stderr）| 効かない | 日本語 |

**旗は記法の言語を選ぶものと宣言し、記法の内側だけを揃える**（2026-08-22 裁定）。印は
記法の内側に入る日本語なので、宣言に従わせる ── 英語記法を選んだのに日本語のコメントが
混ざる状態は、宣言そのものと食い違う。要約・`project.yaml`・申告は日本語のまま残し、
USAGE と SREQ0005 の覆わない範囲へその旨を書く。

成果物全体の英語化は採らない。`project.yaml` の欄名は装飾でなく **`build` の入力仕様**
（FEAT0003）であり、英語化すると別機能の入力仕様へ波及する。憲章の二次ユーザーは
「日本語のブロック表示を前提とする」と明記されている。

### 砦を 2 か所に割らない

`render` は図にする前に 2 つの砦を持つ ── ブロックが 1 つも無い入力を止める砦と、
認識できない記述を止める砦（`src/cli.mjs` の `render`）。`read` の描画経路
（`drawScript`）には無い。同じ判断を 2 か所に書いているのでなく、**片方にしか無い**。
共有して、片方を外すと両方の検査が落ちる形にする。
