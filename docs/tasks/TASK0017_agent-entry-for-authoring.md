エージェント向けの発火点を置く
==============================

## 目的

エージェントがこの道具を使い始める発火点を作る。CLI も知識層も揃っており、
README から手順書までの導線も張ってあるが、その導線は「README を読む」という
契機に依存している。契機そのものは誰も持っていない。

憲章の一次ユーザーは「処理を言葉と設計で表せるが Scratch の GUI 操作には不慣れ」
な所有者である。その所有者が実際に手を動かす相手はエージェントなので、
言葉から記法への道はエージェントが通る。通り道の入口が、いまは偶然に任されている。

TASK0006 が README を根とする導線を張り、その健全さを検査で見張るところまでを
済ませた。本作業はその根を 1 つ増やす。


## 目標

- 「Scratch のプログラムを作る」に当たる依頼で発火し、手順書へ着地するスキルがある
  （SREQ0004）
- そのスキルが持つのは見るものへの案内と実行の形だけで、記法の規則を写していない
  （SREQ0004）
- スキルが指す先（知識層のページ・CLI のサブコマンド）が実在することを、機械で
  見張る（SREQ0004）
- スキルを足したことで、導線の検査の守備範囲に穴が空いていない（SREQ0004）


## 非目標

- 知識層の規則をスキルへ写さない。写した時点で同じ規則が 2 か所に立ち、
  一方だけが古びる。スキルは指すだけに留める
- `read`（既存 .sb3 の読み取り）をスキルの対象にしない。TASK0013 が `read` の
  導線そのものを持っており、着地点がまだ無い。発火語も「作る」と「読む」で
  別なので、1 つのスキルへ束ねると発火の精度が落ちる
- プロジェクト直下の CLAUDE.md を作らない。常時読み込む規定が要るほどの
  分量が無く、必要になってからでよい
- CLI の振る舞い・引数・サブコマンドを変えない。スキルは既存の入口を呼ぶだけである
- 知識層のページを増やさない。手順書・ブロック解説・作品定義の仕様は足りている
- 発火の精度そのものを測らない。発火はホスト側の照合に依るので、こちらから
  観測できるのは形（指す先が実在するか）と、実地で 1 度通ることに限る


## 問題

### 発火点が無い

実測（2026-08-23）。

- `.claude/` の中身は `tmp` だけで、`skills` は無い
- プロジェクト直下に CLAUDE.md が無い
- 追跡下に `.claude` のファイルが 1 件も無い（`git ls-files .claude` が空）

エージェントがこのリポジトリで作業を受け取ったとき、手順書へ辿り着けるかは
README を読むかどうかで決まる。読めば辿れることは TASK0006 が保証したが、
読ませる仕組みは無い。

### 導線の見張りは README を根に固定している

`test/guidance.test.mjs` は入口を 1 つの定数で持ち、そこから辿れる範囲を
「導線」と定義している。

```js
const ENTRY = "README.md"
```

この検査は 2 つを見る。知識層の全ページが入口から辿れること、辿った先の
リンクが実在すること。どちらも根が README である前提で書かれている。

### スキルを足すと、そのスキルの綴りは誰も見張らない

新しい入口を `.claude/skills/` へ置いても、README から指していなければ
上の走査に載らない。載らない入口の中では、次の 2 つが黙って古びる。

| 古びるもの | 起きること |
|---|---|
| 知識層のページへのリンク | ページを移した人が気づかない。スキルが行き止まりになる |
| CLI のサブコマンドの綴り | 綴りを変えた人が気づかない。スキルが動かない例を配る |

後者は既存の検査に相当物が無い。手順書の申告の綴りは実物を動かして照合して
いるが、コマンドの綴りは照合していない。

## 概要設計

### 置き場と名前

`.claude/skills/words-to-scratch/SKILL.md` へ置く。

- 追跡下に入る。`.gitignore` が除外するのは `.claude/tmp/` と

- 名前は TASK0001 の `words-to-scratch-pipeline` と同じ語彙を使う。

### スキルが持つもの・持たないもの

| 持つもの | 理由 |
|---|---|
| 発火の条件（description）| スキルの存在理由。ここだけがホストの照合対象になる |
| 読む順と、迷いの種類ごとに見るものへのリンク | どこから読むかを決める。順序そのものは手順書が持つ |
| CLI の起動形（`render` と `build`）| 実行の形。写すのでなく実物と照合する |
| 自己検査を手順書で確かめるという指示 | 項目そのものは写さない |

| 持たないもの | 理由 |
|---|---|
| 値の型の表・申告の表・記法の例 | 手順書が持つ。写すと片方だけが古びる |
| ブロックの綴り・選択肢 | 台帳から生成した解説が持つ |
| 作品定義のキー | 仕様のページが持つ |

### 導線への載せ方

README に短い節を足し、スキルへリンクする。既存の `reachable()` は README を
根に幅優先で辿るので、スキルはその走査に自然に載る。スキルの中のリンク切れは、
足す検査ではなく既存の検査が拾う。

新しく足すのは、既存の検査が持っていない 1 つだけである ── スキルが挙げる
コマンドの綴りが実物と噛み合うか。

### 綴りの照合の測り方

ソースの `if (command === "...")` を正規表現で拾わない。実物へ渡して測る。

```
node src/cli.mjs <サブコマンド> --help
```

実測（2026-08-23）では `render` / `build` / `read` / `knowledge` がいずれも
終了コード 0、実在しない `nope` が 1 を返す。手順書の申告を実物から集めている
既存の検査と同じ考え方で、綴りの写し間違いを構造的に避けられる。

照合はスキルの側を部分集合として見る。スキルは全サブコマンドを載せないので等号では
測れないが、見るのは「スキルが書いた綴りが全部実在するか」なので、載せなかった
綴りが席を予約することは無い。

## 検証

### 概要

- 綴りの照合は**実物へ渡して測る**。ソースの分岐を正規表現で拾うと、綴りが
  合っていることでなく、正規表現が当たったことを測ってしまう
- 較正を先に置く。抜き出しが 0 件でも通る検査は、スキルが空でも緑を返す
- 破壊は 2 方向へ当てる。守る対象（スキルの綴り・リンク）を壊す向きと、守りの
  側を弱める向きと。前者だけでは、名前が主張する範囲と実際の範囲の差が出ない
- 実地では**機構と動機を別々に測る**。機構はスキルが一覧に現れること、動機は
  そのスキルから `build` が終了コード 0 で終わること。前者だけを見て「効いた」と
  しない
- 発火の精度は測らない（非目標）。実地で外れたら発火語を直すが、直った証明は
  持てないことを申告する

### 段階 5: 実地（2026-08-23）

**動機の側は測れた。** スキルが案内する着地点（手順書と作品定義の仕様）だけを読み、

## 機能への反映

### FEAT0004 記法を書くための知識

外部仕様に次を加える。

- エージェント向けの発火点（`.claude/skills/words-to-scratch/`）を持つ。言葉から
  Scratch の作品を作る依頼で発火し、知識層のどのページを見るかと、CLI の起動の形を
  案内する
- 発火点は規則を持たない。記法の書き方・値の型・ブロックの綴り・作品定義のキーは
  知識層のページが引き続き唯一の持ち手である
- 発火点が案内するサブコマンドの綴りは、実物へ渡して受け取られることを検査が見張る

覆わない範囲として次を宣言する。

- 発火するかどうかはホスト側の照合に依るので、こちらからは測れない
- 発火点が知識層の規則を写していないことは機械で測っていない（語でなく意味の照合に
  なるため）。人が読むときの約束として残す
- 既存の .sb3 を読み解く向き（`read`）は発火点の対象外である
