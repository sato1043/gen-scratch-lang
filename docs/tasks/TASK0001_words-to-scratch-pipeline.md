言葉から Scratch を生成する基盤をつくる
========================================

## 目的

言葉で述べた処理を、日本語のブロック記法・ブロック図・Scratch
プロジェクトファイルの 3 つへ変換できるようにする。3 つが同じ 1 つの
記法から導出されることで、互いに食い違わない状態を保つ。

このプロジェクトの主たる成果は知識（言葉とブロック構成の対応）である。
知識が正しいかを目視でしか確かめられないと静かに腐るため、記述した知識が
そのまま機械検査の入力になる構造を同時につくる。


## 目標

- 日本語のブロック記法から SVG / PNG のブロック図を生成する（SREQ0001）
- ブロックの台帳（日本語ラベル・記法・opcode・引数）を生成し、覆えない
  ブロックを申告する（SREQ0002）
- 記法とプロジェクト定義から .sb3 を生成し、Scratch エディタで開いて
  動かせる状態にする（SREQ0003）
- 言葉からブロック構成を組み立てる知識（ブロック解説・イディオム集・
  手順書）を記述し、その全項目が機械検査を通る状態にする（SREQ0004）


## 非目標

- Scratch エディタ（GUI）の代替を作らない
- Scratch の実行エンジン（VM）を自作しない
- 既存 .sb3 を読み解く利用者向けの解析機能を本作業では扱わない
  （TASK0002 で扱う）。本作業で作るのは往復検査に用いる逆変換の部品まで
- 拡張機能ブロック（micro:bit・EV3・LEGO・音声合成・翻訳・ペン・音楽）を
  本作業で扱わない
- 英語ラベルでの入出力を本作業で扱わない
- 画像・音声素材を作らない。コスチュームは既定の 1 種のみ同梱する


## 問題

達成を阻害する要因を、実測で確かめた事実と未確認の事項に分けて挙げる。

**実測で確かめた事実**

- ブロック記法の解析・描画を担う scratchblocks は、ブロックを l10n の
  識別子（例: `MOTION_MOVESTEPS`）で識別する。一方 .sb3 はブロックを
  opcode（例: `motion_movesteps`）で識別する。両者は機械的に一致しない。
  core 9 カテゴリ 127 件のうち 94 件は小文字化で一致し、30 件は一致しない
  （`OPERATORS_*` → `operator_*` が 18 件、control 系の語区切りが 5 件、
  上流の綴り揺れが 2 件、ブロックでないものが 5 件）。残り 3 件は識別子を
  持たない Scratch 2 の記法
- 記法から .sb3 への変換器は既成のものが見当たらない。逆方向
  （.sb3 から記法）は `parse-sb3-blocks` がある
- Node.js 上での描画には DOM とテキスト計測が要る（`jsdom` + `canvas`）。
  この構成で日本語の記法から SVG が生成できることを確認済み
- 記法はスクリプトしか表せない。スプライトの構成・コスチューム・変数の
  初期値を持てないため、記法だけでは .sb3 を組み立てられない
- .sb3 は各ターゲットに最低 1 つのコスチュームを要求する
- 入力の形は影とブロックの有無で 3 通りに決まる（形 1 = 覆われていない影・
  形 2 = 影を持たない・形 3 = 影を覆うブロック）。出典は scratch-vm 5.0.300 の
  `src/serialization/sb3.js` の `serializeInputs`。形 3 の実物は scratch-parser の
  fixture で確かめた（覆われた影は消えず、値だけが既定へ戻る）
- 影ブロックが値を置く欄の名前は規則で決まる。原始値の表に載る影は表が持つ欄名、
  載らない影（メニュー）は親の入力名と同じ。出典は scratch-vm 5.0.300 の
  `src/serialization/sb2.js`。手書きの表を持たずに済む
- 日本語のラベルは英語と語順が違い、引数を入れ替えて並べるものが台帳 119 件のうち
  8 件ある（`%2 の %1 番目` 等）。台帳の引数は英語の `%1 %2` の順に並ぶため、
  表示の順で素朴に対応させると隣の引数へ値が入る
- zip は決定論的に生成できる。JSZip 3.10.1 で揺れるのは 4 つに限られ（更新日時・
  エントリの並び・同名の重複・圧縮とプラットフォーム）、いずれも呼び出し側で固定できる。
  出典は `lib/generate/ZipFileWorker.js` の `generateZipParts`。日時は `getUTC*` で
  読むため、固定日時を 1 つ与えれば時間帯にも依らない
- 公式検証器（scratch-parser 6.0.1）は構造しか見ない。壊した入力を与えて守備範囲を
  測った結果、コスチュームの欠落・`meta` の欠落・`assetId` の形・入力の形の符号は
  弾くが、実在しない opcode と誤った影の欄名は通す
- 日本語の綴りが衝突する組が 6 組あり、うち 5 件のブロックが記法から呼べない
  （`%1 の長さ` が OPERATORS_LENGTH と DATA_LENGTHOFLIST の双方に当たる等）。
  1 組（`%1 に %2 が含まれる`）は引数の形で見分けが付き、双方とも呼べる。
  どちらが呼ばれるかは段階 4 で解析器へ通して実測した（3-2 の時点では「到達
  できないブロックが 6 件」と書いていたが、測ると 5 件だった）

- 往復検査は影の欄名の誤りを捕まえる。逆変換（parse-sb3-blocks）はメニューの欄を
  名前で引き、知らない欄名に当たると例外で落ちる。段階 3-2 の時点で「欄を名前で
  読まないため一致してしまう」と書いていたが、3-5 の実測で誤りと分かった。ただし
  記法に現れたメニューしか通らないため、別出典から抽出した表との照合は残す

**未確認の事項**

- 影の欄名のうち、記法に現れないメニュー（イディオム集が使わない 12 件のうちの残り）
  は往復検査を通らない。別出典から抽出した表との照合が見張るが、最終的な確認は
  Scratch エディタでの目視に残る

## 概要設計

### 全体の流れ

```
  言葉（会話）
       |
       v   知識層（ブロック解説・イディオム集・手順書）
  記法（日本語）+ プロジェクト定義（YAML）   <-- SSOT・git 管理・人が読む
       |
       v   解析（scratchblocks）
  中間表現（Document）
       |
       +---> 描画 -----> SVG / PNG
       |
       +---> 変換 -----> project.json --> zip --> .sb3
                              |
                              v
                        検証（公式検証器 / 往復検査）
                              ^
                              |
                           台帳（唯一の対応表）
```

### 3 つの決定

**記法を唯一の入力とする。** 記法は人が読み書きでき、差分が読め、解析器・
描画器・日本語辞書が既に揃っている。独自の中間形式を別に持つと記法との
二重管理になり、食い違いの温床になる。.sb3 は生成物であって入力ではない。

**台帳を 1 つだけ持ち、3 出力すべてをそこから導く。** 日本語ラベル・記法・
opcode・引数名の対応が 2 箇所に散ると、図と .sb3 が食い違ってもどちらが
正しいかを決められない。台帳は生成物とし、生成元は次の 4 つに限る。

| 生成元 | 与えるもの |
|---|---|
| scratchblocks の定義表 | 識別子・英語の記法・引数の種別・形状・カテゴリ |
| scratchblocks の日本語辞書 | 日本語ラベル |
| scratch-blocks のブロック定義 | opcode・引数名 |
| 手書きの例外表 | 機械で導けないもの |

opcode 表には Scratch 本体のブロック定義（`scratch-blocks`）を用いる。opcode と
識別子と引数名を同じ場所に並べて持つ唯一の一次情報であり、識別子と opcode の
食い違いも機械で解ける。字句走査に留めて定義を評価しない（評価には Blockly の
実行環境一式が要る）。上流が書き方を変えれば抽出は痩せるが、下の整合検査が
未解決として落とす。

**検査を 3 段に分ける。** 記述した知識が機械で確かめられる状態を保つ。

1. 台帳の整合検査 — 例外表に未使用・未解決が残れば失敗する
2. 往復検査 — 記法から .sb3 を作り、公開実装で記法へ戻して元と比べる。
   生成器の取りこぼしを機械が捕まえる最も強い検査。**比較は文字列でなく
   ブロックの識別子列で行う**。日本語辞書は同じラベルに複数の言い回しを
   別名として認めており、文字列で比べると別名を差分と誤って報告する
3. 公式検証 — 生成した project.json を Scratch 公式の検証器へ通す

Scratch エディタで実際に開いて動かす確認だけは自動化できない。人手の
確認項目として作業書と機能設計記述に残す。

往復検査に用いる逆変換は、テストの中の使い捨てにせず `src/` の部品として
置く。TASK0002（.sb3 の読み取り解析）がこの部品の上に乗るため。

### 記法が持てないものの扱い

記法はスクリプトだけを表す。スプライトの構成・コスチューム・変数の初期値は
プロジェクト定義（YAML）が持つ。1 つの作品は次の形をとる。

```
projects/<作品名>/
  project.yaml     スプライト一覧・変数の初期値・コスチュームの指定
  stage.sbk        ステージのスクリプト（記法）
  <スプライト>.sbk  スプライトごとのスクリプト（記法）
```

コスチュームは自前で生成した最小の SVG を 1 種だけ同梱する。Scratch の
既定素材は持ち込まない（配布物の権利関係を持ち込まないため）。

### 構成

| 置き場 | 内容 |
|---|---|
| `docs/knowledge/` | 知識層。ブロック解説・イディオム集・手順書 |
| `catalog/` | 台帳（生成物）と手書きの例外表 |
| `src/` | 解析・描画・変換・検証・コマンド入口 |
| `projects/` | 作品（記法とプロジェクト定義）|
| `test/` | 自動テスト |

実装は JavaScript（ESM）で書き、型は JSDoc の注釈で表して `tsc --checkJs`
で検査する。ビルド段を持たず素の Node.js で走る状態を保つため。テストは
Node.js 標準の `node:test` を用い、依存を増やさない。

## 検証

### 概要

CP6 の反映まで自動テスト 149 件で確かめた。失敗 0・スキップ 0・警告なし。要と
なる検査は実装を壊して落ちることまで確認した（段階 1 で 5 通り、段階 2 で
5 通り、段階 3-2 で 7 通り、段階 3-3 で 6 通り、段階 3-4 で 2 通り、段階 3-5 で
3 通り、段階 3-6 で 3 通り、段階 4 で 5 通り、CP6 の反映で 3 通り）。うち 3 通りで、
見張るはずの検査が素通りすることが分かり検査を強化した（段階 1・2・3-6 で
1 通りずつ）。自動化できない実機確認は 2026-08-17 にユーザーが済ませた。

公式検証器そのものを較正した。project.json 単体へ壊した入力 6 通りを与え、4 通りを
弾き 2 通りを通すことを確かめた（通すのは実在しない opcode と誤った影の欄名）。
.sb3 全体へも壊した入力 7 通りを与え、5 通りを弾き 2 通りを通すことを確かめた
（通すのは素材の欠落と実在しない opcode）。構造の検査であって意味の検査ではない
ため、これを安全網の主力に置かない。

往復検査も較正した。壊した .sb3 を 6 通り与え、3 通りを捕まえ 3 通りを見ない
（見ないのは入力の値・引数の入れ替え・ドロップダウンの内部値。いずれも値の
取り違えで、構造は壊れない）。

較正の結果はいずれも自動テストの表として置いてあり、検証器や逆変換の挙動が
変われば検査が落ちて記録の陳腐化が分かる。

決定論の検査も較正した。「2 回生成して一致する」検査は、zip の日時の固定を
外しても落ちない。DOS の日時は 2 秒刻みで、同じ実行の中の 2 回は同じ刻みに
入るためである。日時が固定されていることは、ヘッダのバイトを直に見る別の
検査で見張る。

定義の誤りは終了コード 0 で通り、壊れた .sb3 が出ていた。

| 指摘 | 実測で確かめたこと | 直し方 |
|---|---|---|
| 選択肢の照合が `Object.prototype` の名前を素通し | `[toString v]` が問題 0 件で通り、欄が `[null, null]` になる | 持ち物だけを見る |
| 固定選択肢の表が無い入力に日本語ラベルが入る | 背景の `次の背景` がそのまま値になる | 表へ 3 選択肢を足す |
| 触れた判定にスプライト名を書けない | 正当な記法が「選択肢に無いラベル」で止まる | 名前の口を開ける |
| ターゲット名の重複・予約名が無検査 | 同名スプライトで先の宣言が消える | 名前を検査する |
| 定義の値の型が無検査 | `表示: no` が文字列になり、公式検証器が弾く .sb3 が出る | 値の形を検査する |
| 定義の鍵の綴り誤りが黙って通る | `スクリプト名:` で中身の無いスプライトになる | 未知の鍵を申告する |

併せて `.gitattributes` を置き（`autocrlf=true` で clone すると `--check` が誤った診断名で
必ず落ちる）、要求 Node バージョンを宣言した。

検査を 7 件足し、破壊による確認を 3 通り行って 3 通りとも落ちた。`.gitattributes` だけは
自動で確かめられない（clone し直さないと再現しない）ため、覆えない範囲として申告する。

## 機能への反映

### FEAT0001

外部仕様(what):
- 日本語のブロック記法を書いたファイルを渡すと、ブロック図を SVG または
  PNG で出力する
- 記法として解釈できない行があれば、その行を示して停止する

内部設計(how):
- scratchblocks の解析器で中間表現を得て、描画器で SVG を生成する
- Node.js 上での描画に DOM とテキスト計測が要るため `jsdom` と `canvas` を
  用いる

### FEAT0002

外部仕様(what):
- ブロックの台帳を生成する。台帳は日本語ラベル・記法・opcode・引数名・
  形状・カテゴリを持つ
- 台帳が覆えないブロックを件数と一覧で申告する

内部設計(how):
- scratchblocks の定義表・日本語辞書、scratch-blocks のブロック定義、手書きの
  例外表を結合する
- scratch-blocks は字句走査で読む。定義を評価するには Blockly の実行環境が要り、
  得られるものに比して重い
- 例外表に未使用の項目、または解決できないブロックが残れば失敗させる
- 台帳は追跡下に置き、組み立て直したものとの一致を検査する

### FEAT0003

外部仕様(what):
- 記法とプロジェクト定義から .sb3 を生成する
- 台帳に無いブロックを含む入力は、該当箇所を示して停止する
- 同じ入力からは常に同じ .sb3 を生成する

内部設計(how):
- 中間表現を台帳で opcode へ解決し、project.json を組み立てて zip へ収める
- 引数の並び順は解析器自身の綴りから引き直す。台帳の引数は英語の順に並ぶが、
  記法は日本語の語順で並ぶ
- 記法が値を持てないもの（変数とリストの初期値）は定義が宣言し、記法が値を持つもの
  （放送の名前）は記法から集める
- 変数・リスト・放送・ブロックの ID は名前と出現順から導く。無作為な ID を振ると
  同じ入力から同じ .sb3 が出ない
- コスチュームは自前で生成した最小の SVG を 1 種同梱する。`assetId` は中身の md5
- zip は時刻・並び・圧縮を固定して決定論を保つ。同じ素材は 1 度だけ収める

自動化できないテスト項目:
- Scratch エディタでの動作確認
    - 目的: 生成した .sb3 が Scratch エディタで開き、意図どおり動くか
    - 期待結果: 読み込みエラーが出ず、ブロックが意図した並びで配置され、
      実行すると記述どおりに動く
    - 観察方法: Scratch エディタ（ブラウザ）へ読み込んで目視と実行

### FEAT0004

外部仕様(what):
- 言葉からブロック構成を組み立てるための知識を、ブロック解説・
  イディオム集・手順書として読める形で提供する
- イディオム集の各項目は記法を含み、そのまま生成の入力になる

内部設計(how):
- イディオム集の記法を回帰テストの入力として実行し、往復検査へ通す。
  知識の記述と検査の入力を同一物にすることで、記述の陳腐化を機械が捕まえる
- ブロック解説は 2 層で持つ。カテゴリの説明は人が書き、ブロックの一覧は台帳から
  生成して目印の間へ差し込む。一覧を手で書くと台帳と二重管理になる
- 綴りの衝突は、綴りを組み立てて解析器へ通し、どちらが呼ばれるかを実測して申告する

自動化できないテスト項目:
- 手順書の中身が実際に使えるか
    - 目的: 手順に従えば、言葉から記法へ落とせるか
    - 期待結果: 手順の各段で迷わず次へ進め、自己検査項目で誤りに気づける
    - 観察方法: 記法を書いたことのない人が手順書だけを見て 1 つ組んでみる
