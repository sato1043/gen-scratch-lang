自分で作るブロックを通す
========================

## 目的

カスタムブロック（利用者が自分で作るブロック）を、言葉から使えるようにする。

あわせて、実行中に画面を再描画しない指定（`warp`）を持たせる。重い描画がフレーム数に
縛られる状態を解く唯一の手段であり、これが無いと 3D の描画は実用速度に届かない。


## 目的の外にある事実

2026-09-03 時点。いずれも実測または一次情報で確かめた。

| 事実 | 値 | 出典 |
|---|---|---|
| ペンの描画はフレームに同期する | 1 フレームに 1 本 | [実測](../records/20260903_pen-draw-is-frame-synced.md) |
| 粗い 1 枚（48 本）にかかる時間 | 1.6 秒 | 同上 |
| 解析器は `定義` を読める | `PROCEDURES_DEFINITION` を返す | 記法を通して実測 |
| 台帳に procedures の項がある | **無い**（3 件の申告が出る）| `catalog/blocks.json` |
| scratchblocks に `warp` の綴り | **無い**（走査して 0 件）| `node_modules/scratchblocks/` |
| 生成側に mutation の組み立て | **無い**（読み取り側だけが持つ）| `src/` を走査 |
| 読み取り側の mutation の前例 | `procedures_call` を組む | `src/read.ts` |

**ペンのときと構造が違う。** ペンは上流（scratch-vm）に定義があり、写せば済んだ。
`warp` は上流の記法そのものに無いため、**記法をこちらで決める必要がある**。


## 目標

（planning の途中。以下は候補）

- `定義` と呼び出しを台帳へ通し、記法から .sb3 を作れるようにする
- `warp` を指定する手段を持つ
- 往復（読み取り → 生成）でカスタムブロックが保たれる


## 非目標

（planning の途中。以下は候補）

- 3D の作品そのものを作ることは扱わない。手段を用意するところまでを扱う
- 拡張機能ブロック（音楽・micro:bit 等）は扱わない


## 問題

- **`warp` をどう書くか。** 上流の記法に無いので、こちらで決めることになる。記法へ印を
  足す／作品定義で宣言する／既定を決める、のいずれも別の代償を持つ。記法へ足すと
  scratchblocks の綴りから外れ、往復で保てるかを別に確かめる必要がある
- **引数が識別子を持たない。** 記法の `(きょり)` は `custom-arg` として読まれ、
  台帳の枠（識別子 → opcode）に収まらない。台帳の生成元を 4 つに限る設計との整合が要る
- **生成側が mutation を組めない。** `proccode`・`argumentids`・`argumentnames`・
  `argumentdefaults`・`warp` を組み立てる経路が無い。読み取り側に前例があるので、
  そこから形は引ける
- **名前の衝突。** 同じ綴りのカスタムブロックを 2 つ宣言した作品をどう扱うか。ID は
  名前から導く設計なので、衝突すると同じ入力から同じ .sb3 が出る性質と噛み合わない
- **`warp` の効果を測れない。** 今この環境で `warp` 付きの .sb3 を作れないため、
  実装するまで「どれだけ速くなるか」が分からない。実装後に測ることが到達基準に要る


## 到達基準

（planning の途中）

**`warp` の効果を実測して記録する項目を必ず含める。** 機構が動いたこと
（mutation に `warp: "true"` が入る）と、動機が満たされたこと（1 枚の描画時間が
判定の閾値へ入る）は別に測る。

- **CP6 の第三者視点レビューを実施する（提案）。** 台帳・生成・記法の 3 層に跨り、
  往復での保存も要るため、観点を絞らずに測る。実施の可否はユーザーが裁定する
