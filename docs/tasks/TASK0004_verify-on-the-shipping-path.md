出荷する経路に検証の網を置く
============================

## 目的

生成した .sb3 が Scratch で開けることを、出荷する経路そのもので確かめる。
今の公式検証は自動テストの中でしか走らず、掛かる入力は開発者が書いた合成
サンプルに限られる。追跡下の作品もイディオム集の 14 項目も、検証器を一度も
通っていない。

TASK0001 の CP6 レビューで、定義の値の型を誤ると公式検証器が弾く .sb3 が
終了コード 0 で出ることが実測で分かった。型検査は入れたが、網そのものを
出荷経路へ置く判断は残っている。


## 目標

- `build` が書き出す .sb3 を、書き出す前に公式検証器へ通す（SREQ0006）
- 生成した .sb3 が、生成に使った台帳の版と食い違わないことを確かめる（SREQ0006）
- .sb3 を読む側（`openSb3`）に、信頼できない入力への備えを置く

3 項目目は CLI への露出を持たないため単独では採番しない。露出は TASK0002（SREQ0005）が
担う。1・2 項目目は「検査を通っていない生成物を受け取らない」という 1 つの提供価値を
成すため、まとめて SREQ0006 とした（採番 2026-08-18・ユーザー裁定）。


## 非目標

- 独自の検証器を書かない（公式検証器を使う）
- Scratch エディタでの動作確認を自動化しない（人手の確認項目のまま残す）


## 問題

- 公式検証器（`scratch-parser`）は現在 devDependency である。出荷経路で
  使うなら本体依存へ移すことになり、依存が 1 つ増える。移さずに「検証は
  開発時だけ」と決める道もある
- 検証器は構造しか見ない。TASK0001 で実測したとおり、素材の欠落と実在しない
  opcode は通す。網を 1 枚置いても、そこを抜ける型は残る
- `openSb3` は「入力は自分が作った .sb3」という前提で書いてある。TASK0002 が
  他者の .sb3 を読むと前提が反転し、上限も循環検知も無いまま未知の入力に
  当たる（zip 爆弾・`next` の循環）。逆変換の実装にも循環検知が無いことを
  レビューで確認済み
- 台帳は追跡下にあり、生成物は台帳から導かれる。台帳を更新して .sb3 を作り
  直し忘れると、図と .sb3 が食い違いうる。今は照合が無い

- [x] 追跡下の作品とイディオム集の全項目が、この経路で検証を通ることを

- [x] 自動テストが終了コード 0 で通り、警告・スキップの有無を報告に含める

      「すべて推奨で対応」）

1 項目目の**守備範囲**。**`build` の経路で公式検証器が弾く入力を、作品定義から
作れない。** TASK0001 で入れた定義の型検査と名前の検査が先に止めるため、検証器まで
届く不正な入力が無い。コスチュームは既定の 1 種が必ず付き、`meta` は固定値で、
ステージだけの作品も正当に通る（実測）。したがって網は二重化された備えであり、
今日の時点で通せる穴は無い。

網の部品の側は測ってある（弾く・理由を示す・sb2 のエラーを混ぜない・未知の形でも
落ちない）。測れていないのは「網が `build` の経路に繋がっている」ことで、検証の
呼び出しを外しても経路上の検査は落ちない。**この状態を受容する**（裁定 2026-08-18・
ユーザー）。定義の型検査が先に止めるのは良い状態であり、それを崩してまで経路を
測るのは本末転倒だという判断による。読み込みの差し替え（Node 22+ の module mock）で
測る道はあるが、`engines` が Node 20 も許すため環境依存の検査になり、CP6 で
「検証が 1 台の環境でしか走っていない」と指摘された状況と衝突する。


## 概要設計

検証は `build` の出口に 1 枚置く。組み立て → 検証 → 書き出しの順にし、
検証を通らないものは書き出さない。TASK0001 で入れた「問題が 1 件でもあれば
書き出さない」順序と同じ形にする。逃げ道（検証を飛ばす旗）は置かない。旗は
検証器が誤検知したときの避難路になるが、同時に網を空にする経路を自ら作る。

検証器は `--format` の両方で使える。json のときは project.json のバイト列を、
sb3 のときは zip のバイト列を渡す。どちらも同じ関数が受ける（実測）。呼び出しは
テストの中に 2 か所あるので、本体側へ 1 か所に集めて双方から使う。

読む側の備えは `src/roundtrip.mjs` に置く。TASK0002 がこの部品の上に乗るため、
入力の信頼度が反転する場所を 1 か所に集める。

台帳の版は project.json の `meta.agent` へ焼き込む。生成時に台帳を組み立て直して
照合する道は退けた。`scratch-blocks`（台帳の生成元の 1 つ）を本体依存へ引き込む
費用が大きく、かつ生成物の側に版が残らないため、後から .sb3 だけを見ても
どの台帳で作ったか分からない。

焼き込み先の候補は 3 つあり、公式検証器はいずれも通す（2026-08-18 実測・
scratch-parser 6.0.1。`meta.agent` を埋める / `meta` へ独自キー / トップレベルへ
独自キーの 3 通りを json と sb3 の双方で測り、6 通りすべて通った）。よって選択の
根拠は検証器の制約ではない。`meta.agent` を採るのは、公式が「生成した処理系の名」に
使うフィールドで意味が合い、`.sb3` の構造も増えないため。

**エディタの保存に対しては 3 候補とも等価である。** scratch-vm の `serialize()` は
`meta` を毎回新規に組み立て、`meta.agent` へ `navigator.userAgent` を代入する。
読み込んだ値を引き継ぐ経路が無いため、`meta` 配下の独自キーもトップレベルの独自キーも
同じく消える（一次情報・scratch-vm `src/serialization/sb3.js`・2026-08-18 参照）。
当初は「エディタの保存で落ちる懸念が独自キーより小さい」を根拠に挙げたが、これは
比較優位として成り立たない。**照合が効くのは、我々が生成し、一度も Scratch エディタで
保存し直していない .sb3 に限られる。**

## 作業記録

### 段階 1: 出荷経路の検証

`scratch-parser` を `dependencies` へ移し、検証の呼び出しを `src/validate.mjs` へ
集めた。テストの 2 か所に同じ関数が重複していたものを 1 つにし、`build` の出口も
同じ関数を通す。

検証器が弾いたときに渡してくる値の形は 2 通りだった（実測）。zip や JSON として
読めない入力では素の文字列が来る。schema に反する入力では
`{ validationError, sb2Errors, sb3Errors }` が来る。`Error` ではないので `message` は
無い。**`sb2Errors` は報告に載せない。** sb3 の作品を渡しても「`objName` が無い」が
必ず付いてくるため、本当の原因を埋もれさせ、読み手を sb2 の話へ誘導する。

### 段階 2: 読む側の備え

上限の根拠を差し替えた（裁定記録）。展開しながら数えて超えたところで打ち切る形に
した。読み切ってから長さを見ては上限の意味が無い。

JSZip が展開前に持つ大きさ（`_data.uncompressedSize`）は使えない。型定義が
「公開したらここを開ける」と私有であることを明記している。公開されている
`nodeStream` を使うが、`for await` では書けなかった。JSZip 3.10.1 が抱える
`readable-stream` は 2.3.8 で、その `Readable` は `Symbol.asyncIterator` を持たない
（3.x から持つ）。イベントは 2.x でも同じなのでそちらで読む。

循環の探索に**辿る辺の予算**を置いた。当初は予算が無く、検知を外す破壊を当てたら
同期の無限ループへ落ちた。同期のループはイベントループを止めるため、`node:test` の
`timeout` を付けても中断できず、ファイル単位の失敗になって「どの検査が落ちたか」が
集計から消えた。予算を置くと有限で止まり、検査名つきで 3 件落ちるようになった。

### 段階 3: 版の照合

`meta.agent` へ生成器の名と台帳の `生成元` を入れた。書く側（`agentFor`）と読む側
（`stampedCatalogOf` / `catalogDrift`）を同じファイルへ置いた。書式の知識が 2 か所に
分かれると、片方だけ変えたときに黙って読めなくなる。

`out/` は追跡下でないため、「追跡下の生成物が今の台帳と一致するか」という検査は
成立しない。照合が効くのは既にある .sb3 を読むときで、CLI への露出は TASK0002 が
担う。

### 段階 4: 自己コードレビューの指摘を直す

CP5 の自己コードレビューで 4 件が挙がり、いずれも今対応と裁定された（2026-08-18）。

**循環のガードが入口にしか無かった**。`openSb3` では見ていたが、同じモジュールが
別途 export する `toNotation` は無防備で、循環したブロックの表を直接渡すと落ちる。
入口のガードは契機だけを塞ぎ、表を別の経路で組み立てた呼び出し（zip を自分で開く・
一部だけ差し替える）は素通りする。同じ差分のテストが既にその経路を使っており、
TASK0002 もこの部品に乗る。表を受け取る口にも同じ目を置いた。

落ち方は **RangeError ではなくプロセスの abort**（exitCode 134）だった。逆変換の
再帰は `parse-sb3-blocks` の中にあり、こちらから予算を置けない。循環の探索に置いた
予算と違い、未然に防ぐ以外の手が無い。

**理由の組み立てが未知の形で落ちうる**。最後の受け皿が `JSON.stringify(error).slice()`
だったため、文字にできない値（循環参照・BigInt）では例外になる。投げる場所が検証器の
コールバックの中なので、`officialProblems` の promise が解決も棄却もされず、検証の
失敗を報告する代わりに固まる。依存は `^6.0.1` で 6.x の更新が自動で入るため、形が
変わる契機は現実にある。`Error` は名前と本文を、それ以外は文字にできない場合も含めて
受け止める形にした。

残る 2 件は、上限を超えたときに stream を破棄していなかったこと（一時停止だけでは
展開の作業が残る）と、`REASON_LENGTH` を「理由 1 件の長さの上限」と宣言しながら
最も通る分岐に掛けていなかったこと。どちらも直した。

### 破壊で素通りした 3 通り

弾く側の実装へ合わせて 11 通りの破壊を当て、8 通りで狙った検査が落ちた。素通りした
3 通りはいずれも**防御が二重で、片方を外しても他方が受け止める**ことによる。

| 破壊 | 素通りした理由 |
|---|---|
| 参照の照合を `Object.hasOwn` から `in` へ戻す | `Object.prototype` 上の値は関数で `next` も `inputs` も持たないため、辺が空になり結果が変わらない |
| 辺を取る側の形の確認を外す | 参照の照合が先に表の持ち物だけへ絞るため、壊れた値が届かない |
| 辺を取る側の不在の確認を外す | `typeof` の確認が残っている限り `undefined` は弾かれる |

対処として、**表に載っているのに中身が壊れている**入力（`null`・文字列・数値・配列）を
検査へ足した。これで辺を取る側のガードを外すと落ちる。`Object.hasOwn` については
現状のデータで `in` との差を作れないため、防御として残すが検査は無い（守備範囲）。
差が出るのは `Object.prototype` 側に辺を持つ値が生えているときで、それを作るには
prototype 汚染が要る。テスト内での汚染は並行して走る他の検査へ漏れるため採らない。

**破壊が検査名つきで落ちないものが 2 つある**（守備範囲）。循環の検知を外したときと、
`toNotation` のガードを外したときで、前者は予算を置いて解いたが、後者は逆変換の再帰が
外部ライブラリの中にありプロセスの abort になる。どちらも「落ちる」ことは確かめて
あるが、どの検査が落ちたかは集計に出ない。


### 段階 5: 第三者視点レビュー（CP6）の指摘を直す

10 観点を実施し、生の指摘は約 110 件。重複を畳み込んで高 4・中の収束点 6・その他中 15・
低 約 45 になった。詳細は記録（`docs/records/20260818_task0004-cp6-review.md`）が持つ。

セキュリティと性能効率の 2 観点は初回が API エラーで落ち成果物が残らず、再起動した。

**上限とガードを置いた場所が、外部入力が最初に触れる場所とずれていた**。高の 2 件が
この筋に乗る。`openSb3` には上限も循環検知も入ったが、同じ入力が先に通る
`officialProblems` は素通しで、しかも検証器と読み手が別のエントリを `project.json` と
見なしていた。

**検証器と読み手が別の project.json を読んでいた**。公式検証器は
`/^([^/]*\/)?project\.json$/` の先頭 1 件を採り、`openSb3` は名前の完全一致で探していた。
正当な `sub/project.json` を先に置いた zip は検証器を 0 件で通り、`openSb3` はルートの
でたらめな方を読む（実測）。エントリの順序は zip を作る側が選べるため、攻撃者が選ぶ形に
なる。規則を検証器と揃えたうえで、当たりが 1 件でなければ読まないことにした。

**刻印が「誰が押したか」を持っていなかった**。6 観点が独立にここへ到達した。読む側が
最初の `{` から読んでいたため、他所の処理系が `agent` に JSON を載せているだけで自分の
刻印と読み違え、他人の作品に対して食い違いを申告する。生成器の名で錨を打った。

**刻印が「何が変わったか」も持っていなかった**。台帳の生成元は 4 つあり手書きの表は
3 ファイルあるのに、`生成元` が名乗っていたのは例外表の**件数**だけだった。
ドロップダウン表と影ブロック表は版としてまったく現れず、例外表も項目の中身を
書き換えれば件数は動かない。3 つの表の中身から取った指紋に替えた。

**壊れた中身を、読み飛ばす目と直に引く目の両方が見ていた**。辺を取る側は壊れた値を
「辺の無いもの」として読み飛ばすが、記法へ戻す側は `block.topLevel` を直に引く。`null` が
混ざると素の TypeError で落ちる。CP5 で循環に当てた論法（表を受け取る口でも守る）を
中身の壊れにも当てた。

**上限が値によって黙って無効になっていた**。`NaN` との比較は常に false、`Infinity` は何も
超えない。守るはずの値が守らない状態は、上限が無いことより悪いので、使えない値を拒む。

破壊は 8 通り当て、8 通りとも狙った検査が落ちた。指紋については、形と決定論しか
見ない検査は定数でも通るため、**3 つの表それぞれの中身を件数を変えずに書き換えて
版が動くこと**まで測る検査に強めた（例外表だけを覆う指紋へ狭める破壊で落ちることを
確認）。

**指紋が組み立ての引数を見ていなかった**。`buildCatalog` は例外表を差し替えられるのに、
指紋は既定値の側を混ぜており、差し替えた入力が版に映らなかった。staged の差分を読み直す
段で気づいた（検査は既定値でしか呼んでおらず、緑のままだった）。実際に使った表を混ぜる
形へ直し、差し替えが版に映ることを検査に足した。

## 機能への反映

### FEAT0003（.sb3 の生成）

**外部仕様の変更**。

- `build` は書き出す前に生成物を Scratch 公式の検証器へ通す。通らないものは
  書き出さず、終了コード 1 で止まり、違反した場所を示す。検証を飛ばす手段は無い
- 検証は `--format` の両方に掛かる（sb3 は zip のバイト列、json は project.json の
  バイト列を渡す。どちらも同じ関数が受ける）
- 生成物の `meta.agent` に生成器の名と台帳の生成元が入る（これまで空文字だった）。
  同じ入力からは同じ文字列になるため、.sb3 のバイト単位の再現性は保たれる。
  台帳の版は上流 2 つの版と、手書きの表 3 つ（例外表・ドロップダウン表・影ブロック表）
  の中身から取った指紋で表す
- `.sb3` を読む側は、`project.json` の展開後が 5 MB を超える入力と、ブロックの参照が
  循環した入力と、ブロックの中身が壊れた入力を、原因を示して止める
- `.sb3` を読む側は `project.json` を公式検証器と同じ規則（1 段のディレクトリまで許す）で
  探し、当たりが 1 件でなければ読まない。検証器が見たものと読むものを食い違わせないため

**守備範囲**。

- 版の照合が効くのは、我々が生成し、**一度も Scratch エディタで保存し直していない**
  .sb3 に限る。エディタは保存のたびに `meta` を作り直し `agent` を上書きする
- 展開量の上限が掛かるのは `openSb3` の経路だけで、`officialProblems` に生のバイト列を
  渡す経路には掛からない。今日そこへ渡るのは `build` が自分で組んだバイト列に限られる。
  信頼できない入力を検証器へ直接渡す経路は TASK0002 が扱う
- 入れ子の深さに上限は無い。5 MB の線では深さを縛れない（TASK0002 へ送った）
- `scratch-parser` は AGPL-3.0-only で、本体依存の閉包 98 パッケージ中で唯一の強い
  コピーレフトである（`package.json` は `license: MIT`）。`private: true` で公開せず、
  提供するのは生成物（記法・図・.sb3）であってソフトウェア本体を配らないため、
  今は義務が立つ条件に当たらない。**配布またはネットワーク越しの提供を始めるときに
  再判定が要る**

**繰り返し要る確認項目**（この機能を変更するたびに要る。自動化できない）。

- 生成した .sb3 を Scratch エディタで開いて動くこと。`meta.agent` に文字列が入った
  状態で開けること、エディタで保存し直しても壊れないこと
- 公式検証器の版が上がったとき、守備範囲の記録（何を見て何を見ないか）が古びて
  いないこと。記録は `test/sb3.test.mjs` の表が持ち、厳しくなれば検査が落ちる

**設計の要点**。

- 検証器の呼び出しは 1 か所（`src/validate.mjs`）に集める。テストと出荷経路が同じ
  関数を通らないと、テストの緑が出荷の緑を意味しない
- 台帳の版の書式は書く側と読む側を同じファイル（`src/catalog.mjs`）へ置く
- 信頼できない入力への備えは `src/roundtrip.mjs` に集める。TASK0002 がこの上に乗る
