型の宣言を .ts へ移す
======================

## 目的

型注釈を JSDoc から TypeScript の構文へ移し、宣言が実体を写しているかの検査を
強くする。現状は型検査こそ通っているが、注釈に占める `any` が `src` で 25.7%
（769 個中 198 個。2026-08-24 実測。1 個 = JSDoc タグ直後の型表記 1 つ、表記の中に
`any` を含めば 1 個と数える）あり、中核を素通りしている。起票時の「228 個中 87 個
（38%）」は、起票時のコミットを同じ方法で測っても再現しない。数え方の差であり、
以後は上の数え方を正とする。

TASK0005 が `tsc --checkJs` を配線し、宣言と実体の食い違いを 3 件見つけた。
検査が働くことは実証済みで、本作業は同じ検査の網を細かくする。


## 目標

- `src` / `tools` / `catalog` の `.mjs` を `.ts` へ移し、`node` が直接実行できる
  状態を保つ
- 自分の値と、信用しない入力を読む側から `any` を無くす（絶対数で数える）
- `test/` を型検査の対象へ入れる（TASK0005 の M-5 を閉じる）
- 消せない構文が混入しないことを機械で確かめる


## 非目標

- バンドラ・トランスパイラ（tsx・esbuild・swc）を導入しない。Node 24 が
  type stripping を既定で持ち、依存を増やす理由が無い（2026-08-19 裁定）
- 実行時の挙動を変えない。型の宣言を移すだけで、処理の中身は動かさない
- 依存の型定義（`types/externals.d.ts`）の作り直しを主目的にしない
- **B 群（解析器の構文木）と D 群（検査の中）の `any` は据え置く**（2026-08-25 裁定）。
  B 群は上流に型が無く用例からの推定になるため、書いた型が実際の形と食い違っても
  型検査が通り、偽の安心になる。D 群は挙動を検査自身が見張っており効き目が薄い
- **CP6 で受容した 4 件**（2026-08-25 裁定）。いずれも事実として残せば足りると判断した
    - **`.ts` のままではライブラリとして配布できない**。Node は `node_modules` 配下の
      TypeScript を拒む。`package.json` は `private: true` で `files` / `exports` /
      `main` / `bin` をいずれも持たず、配布する道を今は使っていない。使うときは
      別の設計が要る
    - **`npm test` が git バイナリと `.git` の存在へ依存した**。`tools/count-any.ts` が
      追跡下の一覧を `git ls-files` で引くためで、このリポジトリで唯一の git 起動である。
      開発時の走査器であり出荷経路には無い
    - **型剥がしが毎プロセス走る**。軽いモジュールグラフで +60 ms（+51%）を実測した。
      `NODE_COMPILE_CACHE` を置けば旧 `.mjs` と同じ帯へ戻ることも実測済み。CLI では
      依存の読み込み（約 1.6 秒）に埋もれて分解できなかった
    - **`labelCollisions` へ実行時ガード（`if (!block.ja) continue`）を新規に足した**。
      追跡下の台帳は `ja` が空のブロック 0 件なので現状の入力では挙動不変だが、細工した
      台帳では変わる。同じ規則を `sharedLabelsOf` が既に持っており、割らずに揃えた
- **こちらが組み立てて外部へ渡す形（`project.json` の中身・ブロックの表）は `any` の
  まま残す**。C 群の裁定は「信用しない入力を読む側」を指しており、こちらが作る側は
  当たらない。`unknown` を当てると、自分が組み立てた値を自分で絞り直すことになり、
  読みにくくなるだけで守るものが無い。実測で 12 個残った（`project.ts` 6・
  `roundtrip.ts` 4・`sb3.ts` 2）


## 問題

- **type stripping は消せる構文しか受けない**。enum・namespace・パラメータ
  プロパティ・実装を伴う overload が使えない。`erasableSyntaxOnly` を立てて
  機械的に禁じる必要がある
- **import のパスの書き換えが全ファイルへ及ぶ**。`nodenext` は拡張子を要求し、
  `.mjs` を指す import が全部動く
- **`test/` を入れると 309 件出る**（2026-08-24 実測。TS7006 56・TS2532 40・
  TS2554 39・TS2345 39 が上位。全件 `test/` 由来で本体側は 0 件）。起票時の記録は
  221 件だが、当時の数え方が残っておらず、増分か数え方の差かは切り分けていない
  （未測定）。**引数の数の不一致（TS2554）39 件は実害を含まない**。CP2 で切り分けた
  ── 全件が `test/project.test.mjs` のヘルパー `build` の JSDoc に `options` の注釈が
  無いことに由来し、実装 `buildProject(dir, options = {})` は省略可能を正しく宣言
  している
- **移すことと `any` を減らすことは別の作業**である。`.ts` へ移しただけでは検査は
  強くならない。工数の本体は後者にある

## 概要設計

- 足場を先に作る。`tsconfig.json` の `include` へ `.ts` を併記し（`.mjs` と両建て）、
  **`allowImportingTsExtensions` を立てる**。`.ts` を指す指定子はこれが無いと型検査が
  拒む（`error TS5097`。CP3 のレビューで最小の再現を作って実測した）。`noEmit: true`
  が前提条件で、本プロジェクトは既に満たしている。`nodenext` は拡張子を要求し、Node の
  type stripping は指定子を書き換えないため、`.ts` を実拡張子で書く以外に混在期間を
  成立させる道が無い
- 同じ足場で `erasableSyntaxOnly` を立て、葉 1 ファイルだけ `.ts` へ移して通す。消せない
  構文（enum・namespace・パラメータプロパティ・実装つき overload）は現在 0 件
  （CP2 実測。クラス宣言自体が 0 件なのでパラメータプロパティは存在しえない）で、
  最初から立てられる。効いているかは破壊で確かめる（検証節）
- 変換は依存の葉から幹へ向ける。葉を `.ts` へ移した時点で、その importer（まだ
  `.mjs`）の指定子を `.ts` へ直す。この向きなら書き換えは常に未変換の `.mjs` 側で
  起き、変換済みの `.ts` へ戻って再編集しない（幹から始めると、依存が移るたびに
  変換済みファイルの import を直し直す）。書き換え範囲は静的 import 132 文・
  37 ファイルに加え、動的 import 18 箇所と `new URL(..., import.meta.url)` 7 箇所
  （CP2 実測）、および **JSDoc の型参照 `import("./x.mjs")` 18 箇所・5 ファイル**
  （CP3 のレビューで実測。静的 import の目録に入らない別の class で、直さないと
  型検査が落ちる）
- `src` の葉と順序は測ってある（CP3 のレビュー実測）。葉は内部依存 0 の 7 本で、
  被参照数の少ない順に `costume`(1)・`env`(2)・`idioms`(3)・`intake`(3)・`sb3`(5)・
  `definition`(8)・`errors`(12)。段階 1 で通す 1 本は `costume` を採る（被参照 1 で
  足場の検証に要る書き換えが最小）。`errors` は葉だが全体の受け口なので葉の中では
  最後に回す。以降は `notation` → `parse`・`validate` → `catalog`・`render`・
  `roundtrip` → `knowledge`・`serialize` → `project`・`read` → `cli` の順で幹へ向かう
- **`catalog/shadows.mjs` は `src` の変換に含める。** `src/serialize.mjs:16` が
  `../catalog/shadows.mjs` を import しており（CP3 のレビューで実測）、`catalog` を
  段階 3 に置いたままだと `serialize` を移した後で戻って再編集することになり、葉から
  幹の原則が段階の割り方の側で破れる
- 混在期間を許す。全ファイル一括でなくファイル単位で段階的に移し、各ステップの
  終わりで `npm test` と `npm run typecheck` の両方を緑に保つ。`.mjs` から `.ts` を
  import するのは type stripping の既定で動く（`engines >=24.0.0`・CI matrix 24・
  手元 v24.19.0 の全面で既定有効）
- テストの発見条件は `tools/run-tests.mjs:26` の `name.endsWith(".test.mjs")`。
  テストの移設に先立ち `.test.ts` も拾う形へ広げる。書き換えを忘れても、0 件発見の
  ときは 30-33 行が exit 1 で止まるので静かには壊れない（CP2 で現物確認）
- **綴りを焼き込んだ検査が 4 系統ある。参照先が移るステップと同時に直す。** 移設で
  静かに守備範囲が消えるものは無く、いずれも落ちて気づく（CP3 のレビューで 1 件ずつ
  現物確認した）
    - `test/guidance.test.mjs:630-631` が `/src\/cli\.mjs/g` で綴りを固定し、645 行が
      `mentioned > 0` の床を置く。`src/cli.mjs` を移すと SKILL.md の 2 箇所と
      この正規表現を同時に直さないと落ちる
    - `test/dependencies.test.mjs:22` の `ENTRY = "src/cli.mjs"`
    - `.endsWith(".mjs")` の走査フィルタ 4 箇所（`errors.test.mjs:148`・
      `guidance.test.mjs:445,480,501`）。**4 箇所すべてに較正がある**
      （`scanned >= 18` / `>= 15` ×2 / `kinds.size > 0` と等号 58）ので、
      フィルタから漏れれば落ちる
    - `test/cli.test.mjs:21`・`guidance.test.mjs:35` の `CLI` パス
- **利用者が目にする文言に `node src/cli.mjs` が 6 箇所ある**（`src/cli.mjs` の
  USAGE 4 行・`announceRerun` の再実行案内・逃げ道の案内。CP3 のレビューで実測）。
  いずれも固定文字列で argv から組んでいないため、移設すると**実装を直さない限り
  存在しないファイルを案内する**。`test/errors.test.mjs:63-64,75` がこの文言を
  assert している。CP2 が数えた「ドキュメント面 24 箇所」に含まれない別の面であり、
  `.mjs` の扱いの裁定はこの 6 箇所も対象に含める
- `package.json` の scripts 3 箇所と `.github/workflows` の 4 箇所は実在ファイルを
  指すため、参照先が移る段階と同じステップで追随させる（壊れた中間状態を作らない）
- **追随の線は「強制されるか」で引く。** テスト・実行が強制する面（scripts・CI・
  SKILL.md・テスト内の綴り照合・実装の文言 6 箇所）は参照先が移るステップと同時に
  直す。強制されない面（README・知識層・機能設計記述）だけを段階 6 に残す。
  当初はドキュメント面を丸ごと段階 6 へ隔離する設計だったが、検査が SKILL.md と
  実装の文言を強制するため隔離は成立しない（CP3 のレビュー）。**帰結として
  `.mjs` の扱いの裁定は段階 2 の前に要る** ── 裁定前に `cli` を移すと、裁定対象の
  一部（SKILL.md と申告の文言）を既成事実にしてしまう
- `test/` は最後に回す。型検査へ入れると 309 件（CP2 実測。全件 `test/` 由来で
  本体側は 0 件）。TS2554 の 39 件は `test/project.test.mjs` のヘルパー `build` の
  JSDoc に `options` の注釈が無いだけで、1 行の追記でまとめて消える見込み（未検証）。
  残り 270 件は暗黙 any 系 72・undefined/null 可能性系 96 が大半で、本体側の
  型付けで数が動くため先に測っても固まらない
- `any` の削減は「数え方を 1 つに固定してから目標を置く」順序で進める。JSDoc を
  母数にする数え方は `.ts` 化で母数の定義ごと変わるため、移設をまたいで比較できる
  数え方が要る。候補を残課題へ挙げ、どれを正とするかと目標値は裁定を仰ぐ

## 検証

### 概要

- 型検査 0 件と自動テスト全件通過（終了コード 0・スキップ 0 件）を両輪にし、
  移設ステップごとに両方を回す。混在期間も緑を保つ
- `erasableSyntaxOnly` は**破壊で確かめる**。足場の段階で `src` の `.ts` へ `enum`
  を一時的に置き、`npm run typecheck` が消せない構文のエラーで落ちることを見てから
  Edit で戻す（スクリプト越しの置換は不一致を成功として返すため使わない）。戻した
  後に型検査とテストが緑へ帰るまでを 1 つの検証とする。立てただけでは効いているか
  分からない
- テストの発見条件は件数で見る。基準は 2 段構えにする ── 全体の目安は
  **2026-08-24 時点で 460 件**、規則は「各移設ステップの直前に測った値と直後の値が
  一致する」である。段階 4 はテスト自体を触るので固定値だけを基準にすると自分の作業が
  母集団を動かし、基準が腐る。0 件発見のときに run-tests.mjs が exit 1 で止まることは
  CP2 で確認済み
- 動的 import と `new URL` の 7 箇所（子プロセスで cli を起動する系）は静的な
  型検査に映りにくい。cli.test 等の実行が通ることを移設ステップごとに見る
- ビルド段が増えていないことは、`package.json` の `scripts` に変換の段が現れない
  ことと、`node src/cli.ts` が直接動くことで見る
- 混在期間が成立することは実測で裏を取ってある（CP3 のレビュー。Node v24.19.0 が
  `.ts` を直接実行し、`.ts` → `.ts` と **`.mjs` → `.ts`** の import がいずれも
  フラグ無しで動く）。移設の各ステップでこれが崩れていないことは `npm test` が見る
- 利用者が目にする文言（USAGE・再実行案内・逃げ道の案内の 6 箇所）は、移設後に
  実際に `--help` と申告を出させて、案内するパスが実在することを目で見る。
  `test/errors.test.mjs` の assert は文字列の一致しか見ておらず、そのパスが
