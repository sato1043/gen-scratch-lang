既存の Scratch プロジェクトを読み解く
======================================

## 目的

手元にある .sb3 を読み、日本語のブロック記法・ブロック図・構造の要約として
理解できるようにする。子どもが作った作品や共有された作品は .sb3 でしか
手に入らず、中身を読むには Scratch エディタを開いてスプライトを 1 つずつ
辿るしかない。テキストと図に落とせば、読む・比べる・差分を追うができる。

TASK0001 が言葉から作品をつくる向きを担い、本作業が既にある作品を読む向きを
担う。両者は同じ台帳と同じ記法を共有する。


## 目標

- .sb3 を展開し、スプライトごとのスクリプトを日本語の記法として出力する（SREQ0005）
- 各スクリプトをブロック図として出力する（SREQ0005）
- プロジェクトの構造（スプライト・変数・メッセージ・使用ブロック）を
  要約として出力する（SREQ0005）
- 読み取った内容から TASK0001 の入力形式（記法とプロジェクト定義）を
  復元し、生成の向きへ戻せる状態にする（SREQ0005）

## 非目標

- .sb3 の編集・書き戻しを扱わない（読み取りのみ）
- プロジェクトの実行・シミュレーションを扱わない
- 画像・音声の素材そのものの書き出しを主目的にしない
- Scratch のウェブサイトから作品を取得する経路を扱わない
  （手元のファイルを入力とする）


## 問題

- 逆変換の中核（sb3 のブロック定義から日本語の記法へ）は既成の実装で
  賄えることを確認済み。残るのは展開・スプライト構成の復元・要約であり、
  本作業の主たる工数はそちらにある
- 台帳に無いブロック（拡張機能等）が入力に現れる。読み取りは入力を選べない
  ため、生成側と違って「扱わない」で済ませられない。落とさず印を付けて
  出す必要がある
- 復元したプロジェクト定義から再生成した .sb3 が元と完全一致することは
  期待できない（ブロック ID・座標・素材が保存されない）。一致の判定を
  どの単位で行うかを決める必要がある
- **信頼できない入力への備えが、まだ入口の一部にしか無い**。TASK0004 が
  `openSb3` へ展開量の上限・循環検知・壊れた中身の拒否を置いたが、CP6 レビューで
  以下が残ることが実測で分かった（`docs/records/20260818_task0004-cp6-review.md`）
    - 展開量の上限は `openSb3` の経路にしか掛からない。生のバイト列を公式検証器
      （`officialProblems`）へ直接渡す経路は素通しで、182 KB の .sb3 が 2374 ms・
      RSS +241 MB を費やす。**「検証してから読む」順序を採ると上限を迂回する**
    - 入れ子の深さに上限が無い。深さ 2000（JSON 0.25 MB）で逆変換が RangeError に
      なり、5 MB の線では縛れない
    - zip の構造量（エントリ数）に上限が無い。26.2 MB・30 万エントリが通る
    - `openSb3` の `JSON.parse` が裸で、入力の断片を含む `SyntaxError` が抜ける
    - 誤りの伝え方が 3 通りに割れている（`Problem[]` を返す / `throw` /
      `{ stamped, differences }`）。この上に乗ると変換漏れがスタックトレースになる
    - 循環の申告に長さの上限が無い（`src/roundtrip.mjs`。実測 1 行 168,908 文字）。
      TASK0006 から 2026-08-19 に移した（実体が読み取り経路にあるため）
- **逆変換器が知らない opcode は黙って消える**（2026-08-19 実測）。
  `parse-sb3-blocks` 0.5.2 は表に無い opcode を `console.warn("Unknown opcode: ...")`
  だけ出して空文字を返す。落とさず印を付けるには、逆変換に任せず opcode を自分で
  走査するほかない。opcode は被覆で 4 区分に分かれる（2026-08-20 に数え直した。
  数え方は、台帳の 119 件の主 opcode と `alsoCovers` の opcode を合わせた 120 件を
  台帳が知る側とし、台帳自身が `覆わない範囲` へ挙げる 34 件は数えない）
    - 台帳と逆変換器の双方が知る 119 件。読めて、生成の向きへも戻せる
    - 逆変換器だけが知る 88 件（拡張機能 81 と、`control_else`・`data_variable`・
      `data_listcontents`・`procedures_definition`・`procedures_call`・
      `argument_reporter_boolean`・`argument_reporter_string_number` の 7）。
      記法へは落ちるが、台帳に無いので生成の向きへ戻せない
    - 台帳だけが知る 1 件（`sensing_online`）。台帳にあるのに読み取りで消える
    - どちらも知らないもの。消える
- **記法の字下げが指定どおりに出ていない**。`src/roundtrip.mjs` が渡す `tabs` は、
  実装が読む鍵（`tab`）と綴りが違い、既定の 4 空白のまま出る。上流の README が
  `tabs` と書いており、それを写したまま効果を測っていなかった（2026-08-19 実測）。
  読み取りの出力は人が読むものなので、TASK0001 の記法（2 空白）と揃える

## 概要設計

TASK0001 のパイプラインを逆へ流す。台帳・記法・図の生成器はそのまま使い、
本作業で足すのは展開・読解・要約の 3 つに限る。

```
  .sb3
    |
    v  展開（zip）
  project.json + 素材
    |
    +--> スプライト構成の復元 --> プロジェクト定義（YAML）
    |
    +--> スクリプトの逆変換 ----> 記法（日本語）
    |                               |
    |                               v  TASK0001 の描画器
    |                             SVG / PNG
    |
    +--> 集計 ------------------> 構造の要約
                                    ^
                                    |
                                 台帳（TASK0001 と共有）
```

**一致の判定はブロックの識別子列で行う。** ブロック ID・座標・素材は
読み書きの往復で保存されない。これらを含めた完全一致を求めると、意味が
保たれていても不一致になる。判定の単位を識別子列に固定し、保存されない
要素は判定の対象外として明記する。

**記法にできないブロックは印を付けて残す。** 生成側は台帳に無いブロックを
拒否して止まるが、読み取り側は入力を選べない。opcode をそのまま記法の
コメントとして残し、要約で件数を申告する。

印を付ける規則は「逆変換器が知らない」である（2026-08-20 に文言を直した）。
台帳に無くても逆変換器が知る 88 件は記法へ落ちるので、そちらを印にすると
読めているものを「読めない」と申告することになる。印の置き方は場所で分かれる ──
文の位置ならコメントの行、値の枠なら行の途中に残す（コメントは行末までを飲み、
後ろのブロックまで消えるため）。

### 入口と出力

```
node src/cli.mjs read <.sb3> [--out <ディレクトリ>] [--locale ja|en]
                            [--format svg|png]
```

`--out` の既定は `out/<入力名>/`。この下へ 4 種を書き出す。

| 出力 | 名前 | 何を持つか |
|---|---|---|
| 作品定義 | `project.yaml` | TASK0001 の入力形式。復元の到達点 |
| 記法 | `<ターゲット>.sbk` | ターゲットごとの日本語記法 |
| 図 | `<ターゲット>-<番号>.svg` | スクリプトごとのブロック図 |
| 要約 | `summary.md` | 構造の集計と、戻せないブロックの申告 |

全部を組み立ててから書き出す。`build` と `knowledge` が採る規律と同じで、
途中で失敗したときに半分だけ新しい出力が残らないようにするため。

ターゲット名はそのままファイル名にできない（`/` `\` `:` を含む名前を
Scratch は許す）。綴りを写せない名前は、許される文字を数える側の規則で
安全な綴りへ落とし、対応表を要約へ残す。落とした結果が重なったら番号で
分ける（黙って上書きしない）。

### 誤りの伝え方

読む側の口を `Problem[]`（`{ kind, subject, detail? }`）の 1 通りに揃える。
`src/errors.mjs` へ、投げられたものを Problem へ寄せる部品を足し、読み取りの
各段がそれを通す。`openSb3` の throw をやめるのではなく、読む側から見た口を
1 つにする。既存の呼び出し元（往復検査）は throw を期待しており、そちらを
変えると本作業の外へ影響が出る。

### 信頼できない入力への備え

上限は「外部入力が最初に触れる場所」に置く。今は `openSb3` の内側にあり、
公式検証器へ直接渡す経路が素通しになっている。

| 見るもの | 置き場 | 線の引き方 |
|---|---|---|
| zip のエントリ数 | 受け入れ検査（新規）| 費用を実測してから割合で置く |
| project.json の大きさ | 受け入れ検査（新規）+ 既存（`openSb3`）| Scratch 3.0 の 5 MB |
| 入れ子の深さ | ブロックを辿るとき | 逆変換が壊れる深さの手前 |
| JSON の構文誤り | 既存の裸の `JSON.parse` | 入力の断片を報告へ載せない |

受け入れ検査は 1 か所に作り、読み取りの経路と検証器へ渡す経路の双方が
そこを通る。片方だけに置くと、通る順序を変えただけで上限を迂回できる。

**展開後の総量には線を引かない**（2026-08-20 に実測して裁定）。素材だけが膨らむ
.sb3（生 197 KB・展開後 200 MB）は、公式検証器も `openSb3` も 46 ms 以下で通す。
どちらも project.json しか展開しないためで、払われない費用に線を引いても発火しない。
素材が 50 MB ある正当な作品を弾かない線にすると事実上無限になり、守っているつもり
だけが残る。素材を読む経路を足すときに引き直す。

**受け入れ検査は 1 バイトも展開せず、zip のセントラルディレクトリだけを読む。** 申告された
大きさは細工できるので、これは安く弾くための早期の目である。展開しながら打ち切る
既存の `readWithin` が、申告が嘘のときの最後の砦であり続ける。


## 実装計画

| 段階 | 内容 | 主な成果 |
|---|---|---|
| 1 | 入口を固める | 受け入れ検査・上限 3 種・誤りの口の統一 |
| 2 | 読解と記法 | 展開・逆変換・opcode の走査・印・字下げ |
| 3 | 図と要約 | スクリプトごとの図・構造の集計・申告 |
| 4 | 復元と往復 | 作品定義の復元・識別子列での一致の判定 |

段階の順を「問題」節の並びでなく依存の向きで置いた。要約が数える区分は
記法へ付ける印と同じ走査から出るので 2 と 3 は連続させ、最も不確実な復元を
最後に置く。上限は他のすべての段階が通る入口にあるため先頭に置く。

### 段階 1（入口を固める）

- 受け入れ検査を 1 か所に作る。zip のエントリ数・展開後の総量を、開く前に見る
- `officialProblems` と `openSb3` の双方が同じ受け入れ検査を通る形にする
- 入れ子の深さの上限を置く。線は逆変換が壊れる深さを実測してから引く
- `JSON.parse` を包み、入力の断片を報告へ載せない
- 循環の申告の長さに上限を置く（実測 1 行 168,908 文字）
- 読む側の口を `Problem[]` へ揃える部品を `src/errors.mjs` へ足す

### 段階 2（読解と記法）

- `src/read.mjs` を起こす。展開 → 逆変換 → 印付けまでを持つ
- opcode を走査して 4 区分へ分ける。区分の判定には `parse-sb3-blocks` が
  公開する `allBlocks`（207 件）を使う。README が内部実装と断る側に並ぶため、
  版を固定し、区分の件数を検査で見張る
- 逆変換に渡す前に走査する。渡した後では、消えたものが数えられない
- 逆変換器が知らない opcode は記法へ印として残す（`// 読み取れない: <opcode>`）
- 字下げの鍵を `tab` へ直し、TASK0001 の記法（2 空白）と揃える

### 段階 3（図と要約）

- 記法をスクリプト単位へ分け、TASK0001 の描画器へ渡す
- 要約に載せるもの: ターゲット数・スクリプト数・ブロック数・変数・リスト・
  メッセージ・使用ブロックの一覧と件数・4 区分の件数・名前の対応表

### 段階 4（復元と往復）

- 作品定義を復元する。ターゲットの位置・大きさ・向き・表示と、変数・リストの
  初期値は project.json が持つ。コスチュームと音は復元しない（非目標）
- 復元した定義が `build` を通らない入力がありうる（`/` を含む名前は ID の
  衝突検査に当たる）。通らないものは黙って書かず、理由を申告する
- 一致の判定: 元の .sb3 → 記法 → 識別子列 と、復元した定義 → .sb3 → 記法 →
  識別子列 を突き合わせる

#### 測定器そのものが機械に依存していた

最も重い指摘は成果物でなく**検査**にあった。新しい検査 3 ファイルが追跡外の
`out/neko-to-score.sb3` を読んでおり、その作品を作る段はどこにも無かった。隠して走らせると
3 件が落ちる。**それまで報告してきた「N 件成功」は、たまたまその作品が手元に在る機械で
測った値**だった。追跡下の作品から毎回組み立てる形へ替え、再発を止める検出器を置いた。

#### 直した 13 件

落とさない側（不変条件 1・4）。

| 原因 | 何が起きていたか |
|---|---|
| 名前の重なりをファイルシステムと違う形で数える | `Cat` と `cat` で記法と図が終了コード 0 のまま消える（この Windows で実測）|
| 差し替えで `inputs` を空にする | 未知の C 型の中身と値の枠の読めるブロックが消え、集計は数え続ける |
| 生成の向きの検査を読み取りへ再利用 | 公式検証器が通す正当な作品（変数を単独で置いた形）でターゲットが丸ごと落ちる |
| ブロック ID・変数名が `__proto__` | 素の対応への添字代入で持ち物にならず消える |
| `shadow` の自己申告を信じる | 文の並びの影が印なしで消え、集計が「親の行に出る」と嘘をつく |
| 印が綴りでしか守られない | 正当な独自ブロックの名前で偽の印を作れる。読めているブロックが「読み取れない」と申告される |
| opcode の `%` が引数の目印として読まれる | ターゲット 1 つの記法・図・定義が丸ごと落ちる |

入力を信頼しない側（不変条件 5）。

| 原因 | 何が起きていたか |
|---|---|
| 辺の並びをループ内で作り直す | 辺数の二乗。1.1 MB で 25.7 秒、5 MB の内側で 8 分超（直して 30 ms・線形）|
| 終端の注記の長さに厳密一致を求める | **末尾に 1 バイト足すだけで上限 3 種が丸ごと素通り**。読み手は開ける |
| 共有した子を通す | 逆変換が指数展開。ブロック 19 件で 172 ms、1 段 1.7 倍 |
| 既定の置き場を入力の名前から作る | `...sb3` で作業ディレクトリへ書き、根のファイルを上書きする |
| 図の本数に上限が無い | 5 MB の内側に約 39,420 本。1 枚 4.6 ms・29 KB なので約 181 秒・1.1 GB |

#### CP5 の「直した」が狭かった

`Cat` と `cat` の件は、CP5 で私が足した重複の砦を素通りする。砦は文字列の一致で見ており、
**大文字小文字を畳むファイルシステムという戸口を塞いでいなかった**。同じ症状（黙って
上書きする）に 2 つの戸口があり、1 つを塞いで直したと報告していた。

#### 検査が捕まえなかった理由

採番の重なりを CP5 で直したとき、重なりの入力を「落とした結果どうしが重なる」場合でしか
作っていなかった。**採番した綴りが第 3 の名前と重なる**組み合わせも、**大文字小文字だけが
違う**組み合わせも試していない。1 つの原因に対して入力の作り方が 1 通りしか無いと、
直したつもりの範囲がそのまま検査の守備範囲になる。

#### 中は 5 束を反映し、7 束を別作業へ下ろした

裁定を受けて A〜E を反映した ── 要約が申告と食い違う件、定義の検査の穴、印の規則と
文言の食い違い、ファイル名の許可リストの残りの穴、上流の癖を固定する較正である。
F〜L（申告の捨て方・書き出しの原子性・同じ規則の重複・復元が落とす属性・上限の較正・
案内・CI の OS）は別作業へ下ろす。

破壊を 19 通り当て、19 通りとも狙った検査が名前つきで落ちた。

**うち 2 通りは、私の検査が何も測っていないことを暴いた。**

- 升の逃がしを縦棒だけに戻しても検査が緑のままだった。逆斜線を 2 本書いたつもりの
  正規表現が 1 本へ縮み、「逆斜線か空」を表す選択の意味になっていた ── 何にでも当たる。
  逃がしの綴りは文字を組み立てて作る形へ直した（この作業で 5 度目の同じ罠である）
- 上流の癖の較正は、こちらのコードのガードではないので破壊の対象にならない。
  破壊の一覧から外し、前提を確かめる検査として別に扱う


## 機能への反映

### FEAT0005

外部仕様(what):
- .sb3 を渡すと、スプライトごとの日本語記法・ブロック図・構造の要約を
  出力する
- 台帳に無いブロックは opcode を印として記法に残し、要約で件数を申告する
- 壊れた入力は原因を示して停止する

内部設計(how):
- zip を展開して project.json を読み、スプライトごとにスクリプトを
  逆変換する。記法から図への変換は TASK0001 の描画器を用いる
- 一致の判定はブロックの識別子列で行い、ブロック ID・座標・素材は判定の
  対象外とする

自動化できないテスト項目:
- 実物の作品での読み取り確認
    - 目的: Scratch エディタで作った実物の .sb3 を読み、記法と図が元の
      内容と対応するか
    - 期待結果: スプライトとスクリプトが漏れなく現れ、図が Scratch の
      画面と同じ並びになる
    - 観察方法: Scratch エディタの画面と出力の図を並べて目視
