作品定義の仕様を書き、入力の検査を揃える
========================================

## 目的

もう 1 つの入力である作品定義（`project.yaml`）を、記法と同じ水準で扱える
ようにする。記法は台帳・知識層・行番号つきの停止を持つのに、定義は実装だけが
仕様で、書き方を知る手段が実装を読むことしか無い。

TASK0001 の CP6 レビューで、定義の側に「黙って落とさない」規律が及んで
いないことが分かった。キーと値の型の検査はそこで入れたが、仕様の記述と、
記法と台帳の噛み合いの検査は残っている。


## 目標

- 作品定義に書けるキー・値の型・既定値を、読める形で記述する（SREQ0004）
- 記法に書いた引数の形と、台帳が持つ引数の種別の噛み合いを検査する（SREQ0007）
- 名前から導く ID が一意になることを保証する（区切り文字を含む名前で
  衝突しない）（SREQ0007）
- 台帳を読めないときに例外で落ちず、他の問題と同じ経路で申告する（SREQ0007）

## 非目標

- 作品定義の書式そのものを変えない（YAML と日本語のキーを保つ）
- 定義から Scratch エディタの全機能を設定できるようにはしない
  （コスチュームの追加・音の追加は扱わない）


## 問題

- 定義の仕様がどこにも無い。TASK0001 の知識層はブロックの記法を覆うが、
  定義は `projects/neko-to-score/project.yaml` の実例しか手掛かりが無い。
  キーは 11 個あり、うち説明があるのは 4 個
- 引数の種別の噛み合いを見ていない。ドロップダウンを書いた場所が台帳では
  文字列の入力だった場合、今は黙って文字列として通る。日本語の綴りが衝突
  するブロック（TASK0001 で 6 組・呼べない 5 件と実測）を取り違えたときに、
  これが唯一の手掛かりになりうる
- ID は名前から導いており決定論だが単射ではない。`variable:<名前>` と
  `variable:<スプライト>/<名前>` の形をとるため、名前に `/` を含むと別の宣言が
  同じ ID を名乗る。実害は CP2 で確認した（下記）
- `loadCatalog` は台帳が壊れていると例外を投げる。CLI 側には「台帳を読めない」
  受け口があるのに噛み合っていない
- 最上位のキー `名前` は検査を通るが、出力のどこにも使われない。書いた値が効かない
  ことを知る手段が無い

## 概要設計

定義の仕様は知識層（`docs/knowledge/`）へ置く。ブロック解説と同じ 2 層構造を
とり、キーの一覧は実装が持つ表から生成する。散文の説明だけを人が書く。実装と
記述の食い違いは、TASK0001 で入れた `knowledge --check` と同じ形で見張る。

キーの表と既定値は今は別の場所にある。キーは `TOP_KEYS`・`STAGE_KEYS`・`SPRITE_KEYS`
の 3 つが持ち、既定値は `target()` の中に散っている。一覧へ既定値を載せるには
既定値を表の側へ寄せ、生成と組み立ての双方が同じ表から読む形にする。2 か所に
置くと、生成した一覧が実装と食い違っても検査に掛からない。

引数の噛み合い検査は台帳と記法の突き合わせで行う。記法の子が「どう書かれたか」は
中間表現が `shape` として持ち（`dropdown` / `string` / `number` / `color`）、台帳は
引数の種別（`kind` と `notation`）を持つ。照合は直列化の中、引数を台帳の並びへ
対応させ終えた位置へ置く。そこでしか記法の子と台帳の引数が 1 対 1 で揃わない。

照合の規則は素朴に書くと正当な記法を止める。数と文字は Scratch では相互に通り、
放送・音・コスチュームのメニューは選択肢が作品ごとに決まるため台帳側が空になる。
前者は 1 つの類へ畳み、後者は記法の綴り（`%m` で始まる）で見分ける。この 2 点を
入れた規則で既存の記法を測ったところ誤検出は 0 件だった（「CP2 の実測」）。

ID の一意性は、導出の形を変えずに衝突の検出を足す方向で解く。名前を書き換えると
生成物が変わり、決定論の履歴が切れる。検出は宣言をすべて集めた後に ID で束ね、
2 つ以上の宣言が同じ ID を名乗る組を申告する。走査はスプライトを跨ぐ
（衝突はステージとスプライトの間、およびスプライト同士の間に起きる）。

台帳の読み取り失敗は、`loadCatalog` が投げる代わりに問題として返す形へ寄せる。
呼ぶ側は「作品の定義を読めない」を既に同じ形で扱っており、経路を揃えるだけで済む。
壊れた台帳を渡す検査を書けるよう、`buildProject` へ台帳の位置を渡せるようにする。

**引数の噛み合いは中間表現から測れる。** 記法の子は `shape` を持ち、

| 系統 | 件数 | 例 |

| 数を文字の欄へ書いた | 5 | `[スコア v] を (0) にする` |
| 作品ごとに決まるメニュー | 3 | `[はじめ v] を送る`・音の名前 |
