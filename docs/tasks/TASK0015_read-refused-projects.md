検証器が弾いた .sb3 も読めるようにする
======================================

## 目的

Scratch 公式の検証器が弾いた `.sb3` を、読めるところまで読めるようにする。今は
`readSb3` が検証器を先に通すので、schema に合わない作品は 1 ブロックも読めない。
他者から受け取った作品を読み解くという本機能の目的に対して、**受け取れない相手が
いる**状態である。

TASK0002 が「後続で足す」と裁定を受けた項目（2026-08-20）。


## 目標

- 検証器が弾いた作品も、読めるところまで読んで書き出せるようにする（SREQ0005）
- 既定の厳しさは変えない。緩めるのは利用者が明示的に求めたときだけにする
- 緩めたときに**何を保証しないか**を、消えない形で申告する
- 読めない形は緩めても止める。止める線を実測から引く


## 非目標

- 生成の向き（`build`）の検証は緩めない。出荷経路の「検証を飛ばす手段は無い」
  （SREQ0006）は保つ。本作業が触るのは読む向きだけである
- 量の上限は緩めない。受け入れ検査（エントリ数・`project.json` の大きさ・入れ子の
  深さ・循環・共有）は旗の有無に依らず掛かる
- 壊れた作品を直さない。読めた範囲を出すに留め、補完や推測をしない
- 検証器そのものを置き換えない・自作しない


## 問題

**検証器が弾く形の大半は、読める形である**（2026-08-20 実測。24 通りの入力で測った）。

| 変えた形 | 検証器 | 読み取り |
|---|---|---|
| コスチューム 0 件 | 弾く | 2 ターゲット / 2 スクリプトとも読める |
| ステージが先頭でない | 弾く | 読める |
| `meta` / `meta.semver` を落とす | 弾く | 読める |
| `isStage` を落とす | 弾く | 読める |
| `name` を落とす・文字列でない | 弾く | 読める（代替名が当たる）|
| 変数の値が配列でない | 弾く | 読める |
| `variables` を落とす | 弾く | 読める |
| `opcode` を落とす | 弾く | 読める（ただし黙って落ちる。下記）|
| `blocks` を落とす | 弾く | そのターゲットだけ読めない |
| ターゲットが `null` | 弾く | そのターゲットだけ読めない |
| **`targets` が配列でない** | 弾く | **読めない** |
| **sb2 の形** | 弾く | **読めない** |

読めない形は 24 通り中 2 通りだけだった。この 2 通りは、TASK0002 で検証器を
入れる契機になった形そのものである（`targets` が配列でないだけの .sb3 が
「ターゲット 0 件」として終了コード 0 で成功していた）。

**保証が落ちる箇所も測れている。**

- `opcode` を落とした作品は「読める」が、逆変換器がそのブロックを黙って落とす
  （`console.warn` に 1 行出るだけ）。記法と実物が食い違う
- 弾かれた作品から復元した `project.yaml` は、`build` の検証を通らないことがある。
  そもそも検証器が弾いた作品なので当然だが、成果物の側にその断りが無い

**量の上限は旗と独立に掛かる**（実測で確認）。`openSb3` が自分で `acceptArchive` を
呼び、それは検証器を通すより前に走る。逃げ道を通しても資源の防御は外れない。

## 概要設計

- **旗を 1 つ足す**。`read` にだけ付ける。名は `--anyway`（それでも読む）を第一候補と
  する。`--force` は押しつけを含意するので採らない。`build` には足さない
- **検証器を飛ばさず、判定を申告へ降ろす**。旗が無ければ今までどおり止める。旗が
  あれば弾いた理由を申告に載せたうえで読み進む。**検証そのものは必ず走らせる**
  （飛ばすと、何が悪かったのかを誰も言えなくなる）
- **床を置く**。旗があっても、読み取りが実際に要求する形を満たさない入力は止める。
  床は実測から引く ── `targets` が配列であること。それ以外の欠けは、ターゲット単位で
  申告して残りを読む
- **保証しないことを成果物へ書く**。`summary.md` に節を 1 つ設け、旗を使ったこと・
  検証器が弾いた理由・組み立て直せない可能性・記法が実物と食い違いうることを残す。
  申告は stderr へ流れて消えるので、成果物の側にも要る
- 床は「保険」と書いてあった既存のガードが担う。検証器を先に通す設計にしたとき
  到達しなくなったが、逃げ道を足すと再び効くようになる

## 検証

### 結果（2026-08-20）

```

                                    Node 24.19.0・Node 20.19.1 の双方
npm run typecheck                 → 終了コード 0
node src/cli.mjs knowledge --check → 終了コード 0
```

破壊を 13 通り当て、13 通りとも狙った検査が名前つきで落ちた（CP6 の反映後に測り直した値。
反映前は 8 通り）。

| 外したもの | 落ちた検査 |
|---|---|
| 既定の厳しさ（旗が無くても読み進める）| 旗が無ければ、検証器が弾いた作品は 1 件も読まない |
| 同上（CLI から見る）| 旗が無いと、検証器が弾いた作品では 1 つも書き出さない |
| 床（`targets` の形を確かめない）| 旗を立てても、読み取れる形をしていない .sb3 は止まる |
| 受け入れ検査（量の上限）| 量の上限は、旗の有無に依らず掛かる |
| 弾いた理由を申告へ載せない | 旗を立てると、検証器が弾いた作品も読めるところまで読む |
| 要約の断りを出さない | 旗を立てると書き出し、要約に保証しないことを残す |
| 断りを常に出す | 逃げ道を通っていない要約に、断りは出ない |
| ターゲット単位の受け口 | 読めないターゲットだけを落として残りは読む |

**うち 1 通りは、検査が名前どおりのものを測っていないことを暴いた。** 量の上限の検査は
`entries: 0` を渡していたが、0 は「上限として使えない値」なので `refuseBadLimit` が
先に投げていた。落ちる顔（`読み取れない .sb3`）が同じなので緑のまま通っていた。
エントリを 2 件持つ入力へ替え、落ちた理由まで照合する形に直した。大きさの上限を
選ばなかったのは、そちらは展開の側（`readWithin`）でも掛かるため、受け入れ検査を
外しても同じ顔で落ちて外したことが見えないからである。

実機での確認（2026-08-20）。検証器が弾く .sb3 を作り、旗の有無で走らせた。

- 旗なし: 終了コード 1・出力先を作らない・弾いた理由を申告
- 旗あり: 終了コード 1・記法 2 件と図 2 件と `project.yaml` と `summary.md` を書き出し、
  要約の冒頭に断りの節が出る

### 方針

- **既定の厳しさを破壊で確かめる**。旗を渡さずに弾かれた作品を読ませ、終了コード 1 で
  止まり出力先に何も残らないことを見る。旗を足したことで既定が緩んでいないかは、
  緩めた側の検査を何本足しても測れない
- **床を破壊で確かめる**。床を外し、`targets` が配列でない入力が「0 件成功」へ戻る
  ことを見てから戻す。落ちた理由まで見る（終了コードだけでは別の経路でも同じ形で
  落ちる）
- **量の上限を旗の下で測る**。旗を付けた状態で上限を超える入力を渡し、止まることを
  見る。旗が資源の防御を外していないことは、通常の入力では測れない
- 検査の入力は実測した 24 通りから採る。読める形・一部読めない形・読めない形の
  3 種を必ず含める

### 分析（2026-08-20）

原本を 24 通りに壊し、検証器の判定と読めるかどうかを別々に測った。**検証器が弾く

### 実装（2026-08-20）

`readSb3` に `anyway` を足し、検証器の判定を止める理由から申告へ降ろした。検証器は

**終了コードは既存の契約に従った。** `read` は元から「申告があれば書き出しつつ非 0」で

申告の見出しを「読み切れない箇所が N 件ある」から「読み取りに申告が N 件ある」へ
直した。逃げ道を通すと検証器の拒否もここへ入り、全部読めていても件数が立つため、

## 機能への反映

### FEAT0005

外部仕様(what):

- `--anyway` を付けると、公式検証器が弾いた作品も読めるところまで読んで書き出す。
  検証は飛ばさず、弾いた理由を申告してから読み進む
- 旗があっても止まる形がある。読み取りが要求する形（`targets` が配列）を満たさない
  入力と、Scratch 2 の作品は止まる。後者は正体と手当てを名乗る
- 宣言（変数・リスト）の値が読める形をしていないものは落とし、件数と名前を申告する。
  変数はスカラー、リストはスカラーの並びを読める形とする
- 1 度の読み取りが扱うターゲットは 2,000 件まで。超えたら切り詰めずに止める
- 逃げ道を通したときは、`summary.md` と `project.yaml` がその旨と保証しないことを
  申告する。記法（`.sbk`）と図には印を置けない ── 記法にコメントの構文が無く、
  置くと組み立てが止まる
- 保証しないのは 4 つ。Scratch エディタで開けること・`project.yaml` から組み立て
  直せること・記法が実物と一致すること・件数が作品の全体を表すこと

内部設計(how):

- 検証器の判定は、止める理由から申告へ降ろす。検証器そのものは旗の有無に依らず走らせる。
  飛ばすと、何が悪かったのかを言えなくなる
- 床は検証器と独立に置き、検証器が守っていたものを引き継ぐ ── 読める形・宣言の値の
  型・扱う件数の 3 つである。旗が無いときは検証器が先に弾くので保険として残る
- 断りの節と「読み切れなかった箇所」の節は、同じ申告を二重に載せない。分けるのは
  申告の実体の同一性で行う。種類の綴りで分けると、綴りを変えた瞬間に黙って戻る
- ターゲット件数の上限は図の本数と同じ値に置く。どちらも「1 度の読み取りが書き出す
  ファイルの本数」という同じ現象を縛る

自動化できないテスト項目:

- 実在する壊れた .sb3 での読み取り確認
    - 目的: 手元にある古い版や壊れかけの .sb3 を渡し、読めるところまで読めるか
    - 期待結果: 弾かれた理由が出たうえで、読めたターゲットの記法と図が書き出される
    - 観察方法: 実物を渡して出力を目視し、Scratch エディタで開いた内容と見比べる
